# 开源许可与组件合规

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Detailed Design — Open Source Licensing and Component Compliance   ( LD-09 ) · 版本  v0.1 · 2026 年 9 月 · 本册定义组件的选型标准、许可判定与传染性分析、上市年限与 EOL 的举证方式， · 以及组件与版本清单的常设维护机制。

## 1  这一册为什么要早写

本册对应的是投标阶段风险最重的一条。AS-01 记录得很清楚：RFP 1.6.1.27 要求以商用成品形态交付，1.6.1.28 进一步要求产品上市满五年、为 OEM 最新版本、未来五年不 EOL 或 EOS；而本项目是定制开发，不以闭源产品形态交付。项目方针是以核心开源组件公开发布满五年来满足上市年限要求。

这个立场在技术上站得住，但它把举证责任落在了一份东西上——组件与版本清单。HD-00 第 2.4 节写过一句话：这类材料应当从项目第一天起按可举证的标准维护，而不是等需要举证时再补。本册就是那份维护规程。

> 一个已经发生的实例    弃用 MinIO 的原判断理由是 AGPL 许可。复核后发现该理由不成立——AGPLv3 相对 GPLv3 多出的第 13 条以「修改」为触发条件，我方不修改而仅作为网络服务使用，与 PostGIS 的 GPLv2 属同一性质；若以许可为由弃用 MinIO，则同样应弃用 PostGIS。真正决定性的事实完全不同：MinIO 社区版于 2025 年 12 月进入维护模式、2026 年 4 月归档转为只读，最后一次官方安全更新为 2025 年 10 月。如果当初按原理由选中了它，今天整套五年论证就破了一个洞——而破洞的原因与许可无关。这件事直接产生了本册第 2 章的选型标准（DD-46）。 凭方案讨论的记忆去理解需求会漏掉硬指标。条款级的逐条复核不可省略。HD-02 追溯矩阵中"需人工复核的条款"一页保留了 32 条尚未被需求直接引用的条款，开发组应在开工前逐条确认它们确实已被领域需求覆盖。这一页不应长期保持非空。

## 2  选型标准：上游健康度优先于许可

组件选型按下列顺序判断。顺序本身是结论的一部分——许可问题通常可以分析清楚，上游停摆则无解。

| 顺序 | 标准 | 判断依据 |
| --- | --- | --- |
| 一 | 上游健康度 | 治理模式（基金会还是单一公司）、发布节奏、安全响应记录、社区规模 |
| 二 | 许可类型与使用关系 | 见第 4 章的传染性判定 |
| 三 | 规模适配 | 组件自身的运维复杂度是否超过它解决的问题 |
| 四 | 功能匹配 | 是否满足需求，以及有无更轻的替代 |

第三条不是凑数。DD-11 拒绝 Kubernetes、DD-31 拒绝本期引入列存引擎、DD-47 拒绝 Ceph RGW，用的都是这一条：在 27 台虚机、数十用户、按日考核可用性的条件下，多一套需要仲裁、需要滚动升级、需要独立备份恢复与离线补丁链的集群，代价大于收益。

健康度不是选型时评估一次，而是组件清单中的常设字段，按第 8 章的机制定期复核。

## 3  组件与版本清单

权威副本为 Git 中的 compliance/components.csv，随每次组件变更以提交方式更新，提交记录即为维护证据。交付给 MOI 的 Microsoft Office 格式版本由该文件生成，不单独手工维护——两份手工维护的清单必然会分叉。

| 文件 | 内容 |
| --- | --- |
| compliance/components.csv | 在用组件：用途、所在层、许可、OSI 认可、治理、首次公开发布、使用关系、传染性判定、健康度、版本基线、依据 |
| compliance/弃用与不选组件.csv | 曾考虑但未采用的组件及其理由。这一份与在用清单同等重要——评标与合规审查问的往往是「为什么没用某某」 |

版本基线在实施启动时一次性冻结，此后按 REQ-LIC-08 的补丁流程演进，每次变更更新清单。冻结之前的条目标为「待冻结」，不留空白。

按治理模式，在用组件分为两类。基金会或社区治理的：PostgreSQL、PostGIS（OSGeo）、Airflow 与 Superset（ASF）、etcd 与 Keycloak 与 Prometheus（CNCF）、Podman 与 Ansible（Red Hat）、HAProxy、React。单一公司或单一维护者主导、需持续关注的：SeaweedFS、Patroni、WeasyPrint、dbt-core。后一类是第 8 章复核机制的重点对象。

## 4  许可判定与传染性分析

### 4.1  先厘清本项目中「传染」的实际含义

项目方针写的是避免开放源码感染。需要先说清楚这句话在本项目的具体所指，否则容易把不存在的风险当成风险、把真正的风险漏掉。

本项目为定制开发，不交付闭源产品，全部自研代码可以按商务确定的方式向 MOI 交付。因此 copyleft 在这里的实际后果不是「我方代码被迫开源」，而是三条具体义务：

| 义务 | 说明 |
| --- | --- |
| 随附许可文本与源码获取方式 | 交付给 MOI 属于分发，GPL 与 AGPL 组件均须随附。属交付清单事项，无技术影响 |
| 修改部分须以同一许可提供 | 若我方修改了 GPL 或 AGPL 组件，修改部分须以同一许可提供给 MOI。本项目不修改任何第三方组件，故不触发 |
| 不得把 copyleft 代码链接进自研可执行文件 | 这是唯一需要开发纪律约束的一条，见 4.2 |

### 4.2  一条必须写进开发规范的纪律

自研代码只 import 或链接宽松许可的库（MIT、BSD、Apache 2.0、ISC、PSF）；GPL 与 AGPL 组件一律以独立进程或网络服务的方式使用，不进入自研可执行文件的链接边界。

这条纪律的检查点在依赖管理：新增依赖时须在评审中确认其许可，并同步更新组件清单。当前自研代码直接 import 的第三方库只有 WeasyPrint（BSD）、python-docx（MIT）、React（MIT）与可选的 MCP SDK（MIT），全部合规。

### 4.3  逐类判定

| 使用关系 | 涉及组件 | 判定 |
| --- | --- | --- |
| 独立服务（网络协议交互） | PostgreSQL · Superset · Keycloak · SeaweedFS · Prometheus · etcd · Airflow | 不构成衍生作品。许可类型不影响自研代码 |
| 数据库扩展（经 SQL 使用） | PostGIS（GPLv2） | 与调用 GPL 命令行工具同性质，不构成衍生作品。RFP 2.7.3.1 要求的是开放许可与 MOI 的扩展自由，GPL 完全满足 |
| 独立进程与命令行工具 | HAProxy（GPLv2）· Ansible（GPLv3）· dbt-core · Podman | 不链接，不构成衍生作品 |
| 直接 import 的库 | WeasyPrint（BSD）· python-docx（MIT）· React（MIT）· MCP SDK（MIT） | 全部为宽松许可，符合 4.2 的纪律 |

### 4.4  关于 AGPL 的专门说明

AGPLv3 相对 GPLv3 的差别集中在第 13 条：若你修改了程序并让用户通过网络与之交互，须向那些用户提供修改后的源码。触发条件是修改。不修改而仅作为网络服务使用，第 13 条不产生额外义务；交付给 MOI 时随附许可与源码获取方式即可，与 GPL 的处理一致。

本册记录这一分析，是因为 DD-15 曾据此弃用 MinIO 而该理由不成立（见 DD-46）。将来若再遇到 AGPL 组件，按本节判断，不要重复当初的误判。

## 5  上市年限与 EOL 的举证

RFP 1.6.1.28 的三项要求逐条对应如下。

| RFP 要求 | 本方对应 | 举证材料 |
| --- | --- | --- |
| 产品上市满五年 | 全部在用组件的首次公开发布均在五年以上，最短的 Podman 为 2018 年 | 各组件上游的发布历史页面与首个正式版本的发布公告，逐项存档 |
| 为 OEM 最新版本 | 版本基线取上游当前的稳定版本系列，并按 REQ-LIC-08 的流程保持更新 | 版本基线记录与每次补丁的变更记录 |
| 未来五年不 EOL 或 EOS | 以上游治理模式与支持周期政策举证；单一公司主导的组件另附替代方案说明 | 上游的支持周期政策文件；SeaweedFS、Patroni、WeasyPrint、dbt-core 四项另附替代路径 |

MCP SDK 是唯一不足五年的组件，因此它在设计上被限定为可选增补层，移除不影响任何合规项（DD-29）。这一点在举证材料中须写明，避免被当作核心组件质疑。

第三项是最需要主动准备的。对单一公司主导的四个组件，举证材料不应止于「目前活跃」，而应说明如果上游停摆我们怎么办——对象存储只经媒体服务访问因而可替换（DD-47），是这类说明的范例。

## 6  许可条件与部署自由度

| RFP 条款 | 要求 | 本方情况 |
| --- | --- | --- |
| 2.7.3.4 | 许可须永久、非订阅、非按席位、不绑定硬件 | 开源许可天然满足。这是本方相对商用 BI 产品的实质优势，应在应答中正面陈述 |
| 2.7.3.1 | 开放许可，MOI 具备扩展的灵活性 | 全部组件为 OSI 认可的开源许可 |
| 2.7.3.2 | 方案不对安装位置施加任何限制 | 许可与技术上均无位置绑定 |
| 2.7.3.3 | 按接警与主管各 300 席、调度与主管 300 席、JOA 100 席声明容量 | 开源组件无席位许可费用，容量声明不产生额外成本（REQ-PRF-03） |
| 2.7.3.5 | 提供全部软件的完整许可，含第三方组件 | 组件清单与实际部署清单逐项对应，无缺项 |

### 6.1  集中安装、激活与管理（REQ-LIC-07）

RFP 2.7.3.6 要求提供集中安装、激活与管理全部软件许可的方案。开源组件不存在激活的概念，因此本方以组件与版本清单的集中管理替代，并在方案中说明这一替代关系。

具体形态是：Git 中的组件清单为唯一权威；部署时由 Ansible 按清单安装并校验版本；运行中的实际版本由监控采集并与清单比对，不一致即告警。这比商用产品的激活机制提供了更强的可核查性——激活证明的是授权，版本比对证明的是实际部署与承诺一致。这一点值得在应答中说明。

## 7  合同期内的更新与补丁

REQ-LIC-08 要求合同期内保持最新稳定版本，而 CN-12 规定系统运行于无互联网环境。两者存在张力，处置方式是把补丁节奏与离线供给链显式化。

技术栈横跨三个运行时（CN-34），无外网下须维护五条离线供给链：PyPI、Maven、npm、容器镜像仓库、操作系统包源。任一条断供都会使补丁停滞，因此这五条的维护责任、更新频率与验证流程须在 LD-08 中明确到人。

| 环节 | 要求 |
| --- | --- |
| 版本基线 | 实施启动时冻结，记入组件清单 |
| 补丁引入 | 经离线介质导入内网镜像源，导入过程留痕 |
| 验证 | 每次补丁先在测试环境验证，通过后进入培训环境，再进入生产（HLD 12.4） |
| 记录 | 版本变更记录可核查，与组件清单同步更新 |
| 安全响应 | 订阅各组件的安全公告渠道；单一维护者主导的组件另需人工关注 |

## 8  组件健康度的常设复核

MinIO 的教训是：选型时最好用的那个，五年后可能不在了。因此健康度是清单中的常设字段，按下列机制复核。

| 频率 | 对象 | 动作 |
| --- | --- | --- |
| 每季度 | 单一公司或单一维护者主导的组件（当前四项） | 核对上游发布节奏、安全响应与治理公告，更新健康度字段 |
| 每半年 | 全部在用组件 | 核对支持周期政策与版本基线的时效性 |
| 随时 | 出现归档、维护模式、许可变更或治理变更的公告时 | 立即评估，必要时启动替代方案并新增决策记录 |

复核结果写入组件清单并保留历史，本身即是「未来五年不 EOL」这一承诺的持续举证材料。
