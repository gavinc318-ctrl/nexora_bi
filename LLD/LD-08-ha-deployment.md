# 高可用与部署详细设计

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Detailed Design — High Availability and Deployment   ( LD-08 ) · 版本  v0.1 · 2026 年 9 月 · 本册定义集群参数与故障行为、降级决策树、备份与恢复、三套环境、 · 发布与回滚、离线补丁，以及对基础设施提供方的二十一条放置与隔离要求。

## 1  本册的范围与读法

本册细化 HLD v0.3 第 11 与 12 章，回答的是「这套系统怎么活着、出了故障怎么办、怎么装上去、怎么改」。表结构在 LD-02，组件选型与许可在 LD-09，演练与测试用例在 LD-10。

本册有一个不同于其它各册的用法：第 9 章的二十一条放置与隔离要求不是写给开发组的，是写给基础设施提供方的。它们的答复周期最长，且任何一条不能满足，须重新评估相应的服务水平承诺，而不是调整设计。因此本册应当尽早成文并发出，不等其余各册齐备。

## 2  按日考核推出了整个设计

RFP 1.5.2.9 规定数据库为服务等级 1（99.999%），BI、报表与仪表板为服务等级 2（99.99%），且按日考核。这一句是本册全部保守选择的来源。

按月考核可以用一次长故障加二十九天正常来抵消；按日考核不能——一次三分钟的故障就让那一天不达标，而那一天无法被其它天弥补。因此本设计中若干看似保守的选择——同步复制、自动切换、禁止超分、禁止自动迁移——不是保守，是被考核方式直接推导出来的。

这一点在与基础设施提供方沟通时须先讲清楚。否则第 9 章的二十一条要求会被理解为过度设计，而实际上它们每一条都能回溯到这两个数字。

## 3  集群结构与角色

### 3.1  Patroni 是角色变更的唯一权威

这一条必须在虚拟化平台层面得到配合：平台的高可用重启机制不得自行判断并重启数据库虚机。两套独立的故障切换机制作用于同一集群会切出双主，属于数据损坏级别的事故——两个主库各自接受写入，事后无法合并，也无法判断哪一侧是对的。

这不是配置能规避的风险，而是机制冲突。因此它在第 9 章中列为 OP-03，关键级别，须由基础设施提供方书面确认。

### 3.2  关键集群参数

最后一条值得展开。分析副本上长事务的后果不是「那个查询慢」，而是主库的清理被阻塞、WAL 累积、磁盘增长——一个用户的疏忽通过复制链路影响到写入侧。硬超时是唯一可靠的防线，靠规范和培训不行。

## 4  RPO、RTO 与降级决策树

### 4.1  同步复制的两项前提

同步复制使每一次提交都等待网络往返与备库落盘。这一选择成立的前提是两项基础设施条件：主备之间往返时延不超过 1 毫秒（NW-02），数据库数据卷的 99 分位写入时延不超过 2 毫秒（ST-03）。

若这两项在实际环境中无法满足，按下表决策，而不是在故障时临时判断。事先定好决策树的意义在于：故障当下没有时间开会，而临时决定往往是把参数一调了事，事后没有人记得改过。

第三行的措辞是刻意的。把同步改为异步是一次服务水平承诺的变更，不是一次参数调整——RPO 从 0 变成非 0，意味着故障时可能丢数据，而这是写进合同的东西。因此它必须上报，并且留下记录。

## 5  备份与恢复

### 5.1  未经演练的备份不是备份

这一条写在文档里容易，执行起来容易被推迟——备份任务显示绿色，看起来就没事了。但备份真正的失败模式不是「没备成」，而是「备成了但恢复不出来」：归档链断了一段、表空间路径变了、扩展版本不匹配、加密密钥没有一并保管。这些问题只有真的恢复一次才会暴露。

演练记录须包含实际耗时。恢复时间是一个只能实测的数字，而它决定了灾难发生时对业务的答复是「两小时」还是「明天」。

### 5.2  切换演练与恢复演练是两件事

切换演练验证的是 RTO 与自动化是否有效；恢复演练验证的是 RPO 与备份是否可用。两者的失败模式完全不同，不能互相替代——一个自动切换完美的集群，可能有一套根本恢复不出来的备份。两类演练在 LD-10 中各有用例。

## 6  三套环境

### 6.1  两项前置门

RFP 2.7.9.5 规定数据分类政策须经 MOI 批准后，方可在生产与培训环境实施任何数据库；2.7.9.11 规定 DLP 登记册须经 MOI 批准后，方可部署任何数据存储。

这两项是关键路径上的里程碑前置条件，不是可以与开发并行推进的文档工作——未获批准，生产环境无法上线。且两者都需要与 MOI 共同制定而非单向索取，因此启动时间应当早于通常的估计。本方的输入稿在 LD-07 第 9 章。

对本册的直接影响是：脱敏与匿名化的规则要等这两份批准才能定稿，而测试与培训环境的数据准备依赖这些规则。也就是说，前置门不只卡生产上线，也卡测试环境的数据准备——这一点在排期时容易被漏掉。

## 7  发布与回滚

### 7.1  生产网内不部署代码仓库

开发侧 Git 为唯一权威。生产网内既不部署代码仓库，也不自研独立的版本管理工具（DD-49）。理由是：不在 MOI 现场开发，内网 Git 无法与外网同步，本地部署一套仓库既无同步来源又增加一个要维护八年的组件；而自研版本管理工具是在重新实现一个已经有成熟答案的问题。

回滚即从对象存储取回上一制品重新导入，不依赖联网。这一点在无外网环境里是关键——任何需要「从上游拉一下」的回滚方案在这里都不成立。

### 7.2  发布路径与验证

热调与发布的界线要写清楚：凡改变口径、结构或行为逻辑的，一律走发布；凡只改变速率与资源占用的，允许热调。这条界线模糊的系统最终会演变成「在生产上直接改」。

### 7.3  部署方式

部署使用 Ansible 与容器运行时 Podman，不引入 Kubernetes（DD-11）。环境差异以参数区分，不维护多套脚本。

不引入 Kubernetes 的理由与规模有关：本系统是二十余台虚机的固定拓扑，没有弹性伸缩需求，而 Kubernetes 会引入一整套需要专门技能维护八年的控制平面。在一个无外网、由他方运维团队接手的环境里，运维复杂度本身就是可用性风险。

### 7.4  离线补丁与镜像

任何虚机不具备互联网出向访问（NW-03）。操作系统与软件包经内网镜像源分发，镜像更新由离线介质导入并留痕。

五条镜像链都必须在无外网条件下可用，且其更新过程本身要留痕——导入了哪个版本、什么时候、谁导入的。这既是安全要求，也是 LD-09 组件版本基线得以维持的前提：没有受控的镜像源，版本清单在第二个月就会与实际不符。

## 8  资源需求

数据库三台（主库、同步备库、分析副本）各 16 vCPU、64 至 96 GB 内存、4 TB 数据盘，100% 内存预留；etcd 三台提供仲裁；负载均衡、应用、实时、ETL、身份、监控各成对部署；对象存储三节点；备份库一台。

生产环境分两个网络区。内网区 22 台，承载全部数据处理、存储与受控数据交付。DMZ 为 internet 接入区，该区本身连同 WAF、DDoS 防护、公网域名与证书、短信与邮件网关均由总包商提供并运维（CN-30）；本方在该区内只有一件东西——2 台接入代理，为移动端提供 TLS 终止与到内网负载均衡的反向代理（CN-31 · IF-40）。这两台此前未出现在资源表中，是本次补上的漏项（CN-37）。代理不保留任何业务数据与凭据，响应不落盘，访问日志实时外送内网监控，本地只留轮转窗口；移动应用管理（MDM、应用分发、设备合规）由 MOI 既有平台承担，不在本方范围。两台按 TLS 终止的开销各给 4 vCPU、8 GB，所依据的移动端并发规模尚未确认（IR-44 / T-32）——该数字只决定这一对代理够不够用，不影响其它任何虚机。

连接层的顺序是 应用 → pgBouncer → HAProxy → 当前主库（DD-67）。pgBouncer 自己不会找主库，知道谁是主的是 Patroni，HAProxy 读它的 REST 健康检查；把 HAProxy 放在 pgBouncer 之后，pgBouncer 的后端就永远是本机地址，主库易主与它无关。每台 LB 上两个池：业务查询走事务级，Airflow、dbt 与人工运维走会话级——事务级省连接但不保证 SET、临时表与 advisory lock 落在同一后端，而后者正是 ETL 依赖的。会话池的大小即 dbt 的并发上限，两个数必须一起调。LB 对按 active/passive 部署：常态只有一份池在用，但 VIP 漂移的瞬间新接管方会建自己的池而旧连接尚未断尽，因此连接预算按叠加计。据此生产库的 max_connections 由 100 提至 200——不是因为需要 200 个并发，而是要给切换瞬间的叠加与临时人工连接留名额；每连接的固定内存开销在几百 KB 量级，对 64 至 96 GB 的库机可忽略，真正吃内存的 work_mem 由并发查询数决定，而池化之后活跃查询一直很少。

对象存储容量存在五倍差异，这是本册中最大的一个未定量：按低估算（10% 警情携带 3 张照片、每张 2 MB）八年约需 10 TB；按高估算（30% 携带 5 张）约需 50 TB。当前按低估算提出 3 × 8 TB。实际值取决于 MDS 与 E-Assist 现场媒体的真实比例、张数以及是否含视频，需由业务方确认（T-09）。

这个差异要在采购前解决，不能留到实施期。八年期的存储采购按 10 TB 做而实际需要 50 TB，追加的不只是磁盘——三节点对象存储的扩容涉及重新规划放置与备份策略。

## 9  对基础设施提供方的要求

虚机规格本身不产生可用性。主机与存储的隔离方式决定服务等级能否达成。以下二十一条是本设计的可靠性基础，构成对基础设施提供方的输入。

这一章的用法与其余各章不同：它应当整理为接口文件发出，逐条要求书面答复能否满足。任何一条不能满足，须重新评估相应的服务水平承诺，而不是调整设计——设计调整改变不了物理隔离的缺失。

### 9.1  ST-01 是最常被遗漏的一条

仅做主机反亲和是不充分的保护：两台虚机分散在两台主机上，而虚拟磁盘却由同一个 LUN 切出，存储侧一旦故障两台同时失效——而此时同步复制反而使业务完全停止，因为主库在等一个永远不会回来的确认。

这一条必须逐项落实到存储映射表，不能停留在「已做反亲和」这句话上。验收时要看的是 LUN 与控制器的实际映射，不是虚拟化平台上的反亲和规则。

### 9.2  两个机架的固有约束

在只有两个机架的条件下，总有一个机架承载三个 etcd 成员中的两个。该机架整体失效时数据库仍可服务，但自动切换失效，需人工提升。

要在机架整体失效时仍保持自动切换，需要第三个机架或异地仲裁节点。这是仲裁机制的固有约束，配置调整无法规避——三个成员分到两个机架，无论怎么分都有一个机架占多数。若 MOI 要求覆盖这一场景，须在资源上增加第三个故障域，这是一次采购决策而非设计决策。

## 10  服务水平举证

本项目由本方自行举证服务水平达成情况。这可行，但成立的前提是判定口径不能同样由本方单方面决定，否则争议发生时一句「你的测量方法不算数」即可推翻全部数据。

没有事先谈定判定口径的自证，等同于没有证据。建议将本节整理为接口文件，在实施启动前发给总包商确认（T-08）。

举证数据落在 audit schema 的 sla_probe 与 sla_daily 两张表中（DD-45），与业务数据同库同备份，只增不改。放在数据库里而非监控系统里的理由是：监控系统的数据通常有留存期限且可被覆盖，而举证数据需要与考核期一致地保留，并且要能与业务数据在同一次备份中被一并保全。

另有三类故障不计入本方服务水平，须在判定口径中写明：短信与邮件网关（总包商运维）、HudHud 地图服务（第三方本地部署）、AI 包的推断调用（异步或可降级）。三者本方均须留存交接点证据——投递时间、目标网关、返回码、重试次数——否则「不是我方问题」这句话没有支撑。

移动端链路含公网段，不适用 RFP 1.6.7.5 的亚秒承诺，须在判定口径中单列或排除（LD-05 第 8 章）。

| 主库主机失效 | 同上。此时集群暂时无同步备库，按 4.1 第四行临时降级并告警。 |
| 同步备库失效 | 主库继续服务并告警，不阻塞写入。恢复后自动回同步。 |
| 分析副本失效 | 报表查询转向同步备库只读服务。性能下降，界面不中断（与 LD-04 一致）。 |
| etcd 失去仲裁 | 集群进入只读保护状态，不发生自动切换。这是正确行为——没有仲裁时切换就是在赌。须人工介入。 |
| 机架整体失效（两机架条件下） | 数据库仍可服务，但自动切换失效，需人工提升。见 9.2 的固有约束说明。 |
| 网络分区 | Patroni 依据 etcd 仲裁决定归属，少数侧降级为只读。禁止任何绕过仲裁的手动提升。 |

| 编号 | 要求与级别 |
| --- | --- |
| PL-01 关键 | 三台 PostgreSQL 虚机分别位于三台不同物理主机，任何时刻不得两台同宿。 |
| PL-02 关键 | 三个 etcd 成员位于三台不同物理主机。仲裁丢失将使自动切换失效。 |
| PL-03 关键 | 每一对高可用组件（LB、APP、RT、ETL、IAM、MON）至少跨两台物理主机。 |
| PL-04 高 | 三个对象存储节点位于三台不同物理主机。 |
| PL-05 高 | 上述分组跨至少两个机架，机架具备独立供电与独立接入交换。 |
| ST-01 关键 | 主库与同步备库的数据卷位于不同的物理存储；至少不同控制器与不同 LUN。 |
| ST-02 关键 | 备份仓库位于独立于数据库数据存储的介质。 |
| ST-03 关键 | 数据库数据卷厚置备并保证 IOPS，99 分位写入时延不超过 2 毫秒。 |
| RS-01 关键 | 承载数据库与 etcd 的主机不得超分 CPU 与内存；内存 100% 预留，禁用气球与交换。 |
| RS-02 高 | 上述主机的 CPU 就绪时间保持在 5% 以下。 |
| OP-01 关键 | 禁用数据库虚机的自动在线迁移；迁移须人工计划执行。 |
| OP-02 高 | 不对数据库虚机做平台级定期快照。平台快照也不是有效的数据库备份。 |
| OP-03 关键 | 平台高可用重启机制不得与 Patroni 竞争；Patroni 为角色变更的唯一权威。 |
| OP-04 关键 | 全部虚机与 CAD、话务平台使用同一时钟源，漂移不超过 50 毫秒。 |
| NW-01 高 | 复制流量、应用流量与管理流量使用独立网络段。 |
| NW-02 关键 | 主库与同步备库之间往返时延不超过 1 毫秒。 |
| NW-03 高 | 任何虚机不具备互联网出向访问，DMZ 接入代理亦然；补丁经内网镜像源分发。 |
| NW-04 关键 | DMZ 接入代理只接受经平台 WAF 转发的入向流量，向内网仅在指定端口上单向发起；内网不向 DMZ 发起连接。WAF、DDoS 防护、公网域名与证书由平台提供。 |
| RS-03 关键 | 生产库的 max_connections 不低于 200，且 LB 对按 active/passive 部署。连接预算须按切换瞬间两份池叠加计算，不得按常态单份计（DD-67）。 |
| NW-05 高 | 每台 LB 节点上 pgBouncer 与 HAProxy 同机部署，pgBouncer 的后端指向本机回环；HAProxy 的健康检查必须使用 Patroni 的 REST /primary，不得使用 TCP 端口探活——备库端口同样可连，TCP 探活会把写流量送至只读备库。 |
| NW-06 关键 | 内部 CA 能为数据库虚机与负载均衡节点签发服务端证书，且证书中的 CRL 或 OCSP 吊销点在内网可达。库连接与复制流量按 LD-07 第 7 章启用 TLS（sslmode = verify-full）。吊销点若指向外网，离网环境中 TLS 握手不是报错而是超时，表现为连接间歇性卡住数十秒且错误信息不提证书——属最难排查的一类故障。另须给出证书的轮换周期与通知方式。 |
