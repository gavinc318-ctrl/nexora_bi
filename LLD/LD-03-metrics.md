# 指标与口径详细设计

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Detailed Design — Metrics and Definitions   ( LD-03 ) · 版本  v0.1 · 2026 年 9 月 · 本册定义指标的粒度与聚合、日切封账与修正、口径版本机制、 · 对账规则，以及指标注册表的权威位置与维护方式。

## 1  本册的范围与读法

本册细化 HLD v0.3 第 6 章，回答的是「一个数怎么算出来、算的是什么、什么时候算完」。表结构在 LD-02，接口在 LD-04，逐张报表的版式在 LD-05A。

指标定义以 YAML 形式交付，不在正文中逐条罗列。权威副本为 Git 中的 metrics/metrics.yaml，当前 59 条；库内的 meta.metric_registry 是部署时同步的只读副本。

| 文件 | 内容 |
| --- | --- |
| metrics/metrics.yaml | 59 条指标的完整定义：粒度、聚合方式、度量表达式、归日依据、维度、来源表、版本、是否依赖未验证映射、是否回溯类、是否已发布 |

相对 HD-05 的 52 条初稿，本册做了三类调整：把「单警」这一含糊粒度按五层单据树重新落位；把同一名称下不同定义的指标拆成各自的编码；补入手动关闭与数据质量相关的新指标。

## 2  粒度是本册最重要的一件事

### 2.1  单据树决定粒度

CAD 的单据是一棵树：接警单、派警单（每警种一张）、出警单（每警员一张）、反馈单（每警员多张）。时长类指标的落点由这棵树决定，挂错层就不是同一个数。

| 指标 | 起止 | 粒度 |
| --- | --- | --- |
| 受理时长 M-I03 | 首呼应答 → 接警单建立 | 接警单 |
| 派单时长 M-I04 | 接警单建立 → 派警单下发 | 派警单（每警种一个数） |
| 到场时长 M-I05 | 派警单下发 → 该警员到场 | 出警单（每警员一个数） |
| 处置时长 M-I06 · M-I22 · M-I23 | 到场 → 本出警单结束 | 出警单 |
| 全过程时长 M-I08 | 首呼振铃 → 全案结案 | 接警单 |

由此推出一条最容易算错的：M-R05 警员出动次数按出警单计——一张派警单出三名警员即三次出动。R-24 处置单位出动与负荷同理。

### 2.2  三个到场时长是三个定义，不是三种平均

「平均到场时长」这句话在多警种警情上是无意义的。但正确的处理不是给同一个数取三种平均，而是承认业务在问三个不同的问题：

| 编码 | 问的是什么 | 怎么算 |
| --- | --- | --- |
| M-I05 到场时长（按出警单） | 每名警员各自用多久到场——资源效率口径 | 逐张出警单，可取均值、中位与 P90 |
| M-I20 警种到场时长（按派警单） | 这个警种多久到的——响应口径 | 该派警单下最早到场的那一张出警单 |
| M-I21 首个到场时长（按接警单） | 多久有人到现场——响应口径 | 全案跨警种最早到场 |

后两个用最早到场而不是平均，理由是业务含义：后到的警员属增援，把增援时间平均进去会让「响应时长」不再是响应时长。这一点在设计讨论中曾按三种平均处理，复核后改为三个定义——数值与口径都更站得住。

### 2.3  一个实测例子

以一起同时派给警察与民防、共出动五名警员的警情为例，在样例数据上实测：按出警单平均为 15.20 分钟，按派警单平均为 14.17 分钟，按接警单取首个到场为 6.00 分钟。

> 三个数都对，回答的是三个不同的问题    因此 meta.metric_registry 的 grain 列为非空，metrics.yaml 中 grain 与 aggregation 两项必填，缺任一项不得合并。含糊其辞的「平均到场时长」不允许进入指标注册表，报表标题与口径说明中必须写明按什么粒度、用什么聚合。 凭方案讨论的记忆去理解需求会漏掉硬指标。条款级的逐条复核不可省略。HD-02 追溯矩阵中"需人工复核的条款"一页保留了 32 条尚未被需求直接引用的条款，开发组应在开工前逐条确认它们确实已被领域需求覆盖。这一页不应长期保持非空。

## 3  手动关闭带来的三处后果

派警单与出警单在 CAD 上由人工关闭。结构上不受影响，口径上有三处后果，都必须显式处置。

### 3.1  时长含操作员延迟，故主口径用中位数

ended_at 是点击关闭的时间，不是实际处置结束的时间。会有系统性长尾——下班前批量关单、忘了关到第二天。

处置方式是不作截断以保真，改为拆成三个指标并列呈现：M-I06 均值、M-I22 中位数、M-I23 P90。对外发布的主口径是中位数，因为均值受长尾污染最重。指标定义中写明「以关闭时间为准，含操作员延迟」，这句话须出现在报表脚注上。

### 3.2  归日：发生类按事件日，结案类按关闭日

跨日关闭的单据按哪个日期归属，结论不同。因此 fact_dispatch_order 与 fact_turnout 各增加一列 closed_date_key，与作为分区键的 date_key 并存。

| 类别 | 指标举例 | 归日依据 |
| --- | --- | --- |
| 发生类 | 当日派单量、当日出动量、警情量 | date_key（事件日，也是分区键） |
| 结案类 | 当日结案数 M-I24、处置时长 M-I06 至 M-I23、全过程时长 M-I08 | closed_date_key（关闭日） |

不加这一列的话，「当日结案数」只能按事件日算，跨日关闭的单子会记到发生那天——那不是业务想看的数。

### 3.3  未关闭的单据

未关闭的出警单排除出处置时长的分母，同时单列两个数据质量指标：M-R08 未关闭出警单数、M-R09 最长未关闭时长，进 D-16 数据质量看板。

两者与处置时长并列呈现，目的是避免「时长看着不错」掩盖「两百张单子没关」。

## 4  日切、封账与修正

结案类指标按关闭日归属之后，封账变得干净：每一天的结案数在封账时天然完整，因为结案日就是关闭日。不需要完成率，也不需要为此建修正机制。

| 类别 | 封账行为 |
| --- | --- |
| 发生类 | 封账即完整，此后不变 |
| 结案类 | 按关闭日归属，封账时该日的关闭均已发生，故亦为完整值 |
| 迟到数据 | 接入侧的迟到（数据同步滞后）仍按 HLD 6.3 进修正表并递增版本，与关闭时间无关 |

### 4.1  一个必须显式登记的例外：回溯类指标

业务迟早会问「9 月 6 日的警情最终结案了多少」——那是按发生日看结案率，数值会随时间推移而变化，今天看是 78%，下个月看是 96%。

这类指标允许存在，但必须在注册表中标注 retrospective 为真，报表上写明「截至查询时点」。当前仅 M-I25 一条。数量须严格控制：一旦回溯类指标蔓延，「报表可复现」就名存实亡。

## 5  指标注册表的形态与权威

权威在开发侧 Git 的 metrics/metrics.yaml，走提交与评审；库内的 meta.metric_registry 是部署时同步的只读副本；M-04 指标字典界面只读。这与接入契约用的是同一个模式（DD-05）。

理由是口径属于结构性配置。如果能在管理界面上点一下改掉，事后就查不清当时用的是哪一版——而封账机制的全部意义正是「去年打印的报表今年重跑一致」。

发布随 DD-49 的制品流程：指标定义与契约、模型、DDL、部署脚本、组件清单一同打包，带版本号与校验和，manifest 中携带变更摘要与评审记录，登记入 meta.release_registry。

## 6  口径版本

metric_version 递增即意味着「同一个指标，换了算法」。什么算口径变更须定死，否则版本号会失去意义。

| 变更 | 是否递增版本 |
| --- | --- |
| 分母定义、过滤条件、时间边界、粒度、聚合方式 | 是 |
| 新增可用维度 | 否 |
| SQL 重写但结果集恒等（性能优化） | 否 |
| 上游映射由 mapped_unverified 转为 verified | 否，但 depends_unverified 标志翻转 |

递增版本的指标，历史报表不自动重算——旧版本的数保持原样，新版本自生效日起用。否则「去年打印的报表今年重跑一致」这条守不住。口径变更须走评审，评审记录随制品进入生产。

## 7  响应元字段与成熟度标记

查询 API 的每一次响应携带四个元字段：口径版本、数据时点、封账状态、是否依赖未验证映射（HLD 6.5）。这四个字段使给出的数字成为可以在会议上被辩护的数字——数值到达时同时带着产生它的规则以及它有多确定。

metrics.yaml 中 depends_unverified 为真的共 9 条，其中 8 条在依赖解除前 published 置为假；其余 1 条带标记发布，报表上须呈现「依赖未验证映射」的脚注。原先依赖 IR-11 的 8 条话务明细指标中，6 条已随 CloudICP 接口文档到手而解除依赖并发布，剩下 M-C08 与 M-C14 两条另有原因，见第 10 章。

## 8  对账规则

对账的目的是让差异被发现并被解释，而不是让差异消失。三类对账各有其不可替代之处。

| 对账 | 比对对象 | 处置 |
| --- | --- | --- |
| 话务类总量 | 本系统与话务平台自身的报表 | ICP 无第二条技术通道，这是唯一的交叉验证手段。每日自动比对，差异记录并留痕 |
| 辖区归属 | CAD 的辖区字段与本方按区划面的空间计算 | 以 CAD 字段为准（DD-32）。空间计算仅作对照，一致率作为数据质量指标监控 |
| 实时与封账 | 大屏的指示性数字与日结报表的权威值 | 差异是两条路径的固有属性，不是缺陷。纳入每日对账报告，超阈值告警（HLD 6.4） |

第三类值得强调：实时路径按轮询周期采样、不做去重与软删除处理，统计路径做。把这个差异写明白，比让使用者自己发现要好。

## 9  热点与聚集区

HLD 8.2 明确写了算法与阈值在详细设计阶段与业务确认。本册的处理是把它们做成配置项，先给建议值，业务确认后即可调整而不改代码。

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| 网格边长 | 500 米 | 在 srid_analysis（UTM 37N）投影下计算。经纬度直接算面积在麦加纬度会明显失真 |
| 时间窗 | 滚动 7 天与滚动 30 天两档 | 短窗看当前聚集，长窗看稳定热点 |
| 热点判定 | 相对基线而非绝对数 | 绝对数会让人口密集区永远是热点，失去指示价值 |
| 最小样本量 | 网格内不少于 5 起 | 低于此不判定，避免小样本噪声 |

M-I13 热点强度的粒度是网格时窗，与其它指标不同，因此单列。呈现由 HudHud 的嵌入式组件承担，本方只出聚合结果（CN-29 · CN-32）。

## 10  依赖未决事项的指标

metrics.yaml 中 depends_unverified 为真的共 9 条，其中 8 条在依赖解除前 published 置为假；其余 1 条带标记发布，报表上须呈现「依赖未验证映射」的脚注。原先依赖 IR-11 的 8 条话务明细指标中，6 条已随 CloudICP 接口文档到手而解除依赖并发布，剩下 M-C08 与 M-C14 两条另有原因，见第 10 章。

| 依赖 | 涉及指标 | 未解除的后果 |
| --- | --- | --- |
| IR-11 ICP 五类话务明细（已答复） | 原 M-C08 至 M-C15 共 8 条，现余 M-C08 · M-C14 两条 | CloudICP V100R023C00 接口文档确认 ICP 提供原始话单而非仅状态快照，M-C09 至 M-C13 与 M-C15 六条改为由话单自算并发布，R-04 至 R-07 不再因此作废。余下两条另有原因：M-C08 振铃次数在话单与平台指标中都不存在，按原口径不可交付，须与 MOI 改口径；M-C14 骚扰标记只可能来自人工操作，来源未定（IR-46）。R-03 仍悬于 M-C08。 |
| IR-09 ICP 是否提供历史事件接口 | M-R03 状态时长 | 仅有当前状态快照时精度被轮询周期锁死，须在报表上标注测量方式 |
| IR-41 CAD 资源状态的落库形态 | M-R06 资源可用率 | 仅有派单快照而无状态时间序列时，本指标无法计算，R-25 与 D-04 受影响 |
| IR-28 客户反馈的采集方与形态 | M-P03 至 M-P05 | D-15 客户反馈看板与 R-31 无数据来源 |
| 不在项目范围 | M-P02 质检得分 | 复核与质检属 IRMS（RFP 2.3.9.7），本系统既不采集也不计算。条目保留仅为说明该口径的归属，永不发布（DD-55） |
| IR-03 软删除的表达方式 | M-I11 撤案数 | 源端若为物理删除，撤案统计与 CAD 自身长期不一致且无法解释 |

这些指标的定义已经写好并进入注册表，只是未发布。依赖解除后翻转标志即可，不需要重新设计——这与接入契约的处理方式一致：答复到位后改的是配置，不是代码。
