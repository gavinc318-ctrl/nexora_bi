# 约束与设计决策登记册

## 说明

HD-04  约束与设计决策登记册

本表把两类容易在交接中丢失的信息固定下来：系统受到的约束，以及做过的选择与放弃的选择。

约束登记册

每条约束标明来源与类型。"RFP 强制"与"RFP 前置门"两类不可协商；"RFP 开口"表示条文留了口子，须在设计阶段冻结；"现场条件"与"商务"来自项目实际；"技术固有"是无法通过配置规避的限制。

注意 CN-13、CN-14 与 CN-15：前两条是关键路径上的前置门（未经 MOI 批准不得上生产库），第三条是合同授予后两个月的硬期限。这三条应在项目计划中作为里程碑约束，而不是普通任务。

设计决策记录

"被拒绝的方案"与"拒绝理由"两列是本表的核心。交接时最容易丢失的不是做了什么，而是为什么没做另一种做法——缺了这个，后来的人会把已经权衡过的方案重新提一遍，或者在不知情的情况下把某个刻意的约束改掉。

"可逆性"列标注该决策事后更改的代价。标为"高"的决策一旦落地，更改属于架构级或重构级工作，变更前应重新评估。

DD-24 与 DD-25 是本次整理交接包、逐条复核 RFP 条款时对既有判断的推翻。两条都保留了原判断与推翻理由，作为"条款级复核不可省略"的实例。

DD-28 与 DD-29 为详细设计阶段第一轮讨论新增：前者确定 AI 能力的交付边界与四向集成接口，后者确定 MCP 的定位与版本冻结纪律。按 HD-00 第 6 章的维护规则，两条为新增而非修改既有记录。

CN-28 至 CN-31 与 DD-30 为详细设计第一轮讨论新增：AI 包与 HudHud 的联合体划界、DMZ 与两个外部网关的归属、移动端经 DMZ 外联的边界，以及移动端方案对 DD-14 选型依据的推翻。

CN-01 于详细设计第一轮讨论中就地修订：类型由「RFP 强制」改为「RFP 要求（解读）」，并注明该解读不得写入投标文件。相应的架构立场记于 DD-31。CN-32 与 DD-31 至 DD-33 为同一轮新增。

DD-34 与 DD-35 为详细设计第一轮讨论新增：补上 RFP 1.6.2.7 要求而 HLD 未承载的记录级检索能力，以及随之必需的字段级可见性矩阵。行级安全（REQ-SEC-03）维持预留不启用。

DD-36 为详细设计第一轮讨论新增：响应时间三档分层，快速路径以近一年数据为界。该决策同时降低了 DD-31 中列存加速层第二条触发条件的发生概率。

DD-37 至 DD-39 为详细设计第一轮讨论新增。其中 DD-38 纠正了 HLD 5.5 与 REQ-BAK-04 对 RFP 2.7.10.4 的口径误读，属条款级复核发现的第三处更正，性质与 DD-24、DD-25 相同。

CN-33 与 DD-41 记录 AS-14 的推翻：四角色不变，但调度员与主管按派驻部门切分数据。DD-19 的预留在此兑现，故本次为启用而非重构。DD-40 同轮新增。

DD-43 至 DD-48 与 CN-34 为组件选型讨论新增。其中 DD-46 修正了 DD-15 弃用 MinIO 的理由——原以 AGPL 为据不成立，真正的理由是上游已归档停止维护；该条同时确立「上游健康度优先于许可」的选型标准。按维护规则，DD-15 保留原文不改。

CN-35 与 DD-49 补上了一处漏项：HLD 9.2 以「Git 为权威」为前提，但组件清单与虚机资源表中从无代码仓库。结论是生产网内不部署，改由发布制品、对象存储中的历史版本与 meta.release_registry 承担。

DD-50 补正 DD-35 的缓存键定义——原规定只挡住列的串号，挡不住行的。DD-51 改变了受控 SQL 的授权方式：由按角色改为按自然人显式授权，系统一律经服务层不另开通道。按维护规则 DD-35 与 DD-18 保留原文不改；DD-51 在同一轮讨论中定稿，系统主体一案记入其被拒绝的方案列。

CN-36 与 DD-52 更正了归档库的数据库产品：为 SQL Server 而非此前记录的 PostgreSQL。这是一条已确认客户答复被推翻的实例，连带影响接入连接器、接口协议、类型映射、插图与组件清单。

【2026-09 补充】DD-53 至 DD-55 为详细设计第二轮讨论结论：旁路数据源经逐项核实后清空——排班改派生、勤务级别保留非必选接口、质检属 IRMS 不在范围。本系统因此不存在人工录入的业务数据源，M-10 仅维护参照数据。
