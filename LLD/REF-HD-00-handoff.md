# 开发交接说明与文件索引

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Handover Guide and Document Index   ( HD-00 ) · 版本  v0.1 · 2026 年 9 月 · 先读这一份。它说明其余文件各自回答什么问题、按什么顺序读、 · 哪些内容可以直接依赖、哪些必须先去确认。

## 1  交接包的结构

投标阶段产出的设计文档（HLD）是给评标人看的：它要证明方案可行、覆盖条款、技术选择有理由。开发组需要的是另一套东西：条款级的需求、可验收的标准、哪些前提是假设、哪些信息还没有、以及为什么当初没有选另一种做法。这个交接包补的就是后者。

| 文件 | 回答什么问题 | 格式 |
| --- | --- | --- |
| HD-00 开发交接说明与文件索引 | 先读哪一份，各文件的分工，哪些内容可以直接依赖 | 本文件 |
| HD-01 需求规格说明书 | RFP 要求转写为编号需求，每条有验收标准。条数以该册为准，不在本表重复。 | Word |
| HD-02 需求追溯矩阵 | RFP 条款逐条对应到需求编号、HLD 章节与 LD 册章；开发状态跟踪。条数以该册为准。 | Excel |
| HD-03 假设与信息需求登记册 | 假设的依据与推翻后果；待收集信息的对象与用途。条数以该册为准——每次新增都要回来改数字，迟早会漏。 | Word |

### 1.1  建议的阅读顺序

HD-00（本文件），约二十分钟。了解交接包的结构与四处已知冲突。

HD-03 假设与信息需求登记册。**先读这一份再读需求**。知道哪些前提是假设，才不会把假设当成事实去实现。

HD-01 需求规格说明书第 1 与第 2 章，然后按负责领域读对应章节。

HLD 全篇。此时读架构，每一个设计选择都能对应到某条需求或某条约束。

HD-04 设计决策记录。在准备改动任何架构决定之前必须读——"被拒绝的方案"一列记录了已经权衡过的路径。

HD-02 与 HD-05 作为工作时的查询工具，不必通读。

## 2  四处必须先知道的事

下列四项在早期设计讨论中未被识别，是在整理本交接包、逐条复核 RFP 条款时才发现的。前两项已在本交接包中修正，后两项需要商务处置。

### 2.1  报表与仪表板的数量是四十与二十，不是三十与十二（已修正）

RFP 1.6.2.25 规定每个中心四十张自定义报表与二十个仪表板，是硬数字。早期设计文档中的"三十张报表、十二个仪表板"来源于方案讨论而非条款，已作废。HD-05 按四十加二十编制；HLD v0.2 的 7.4 与 8.2 已相应更正。

遗留问题：RFP 1.6.2.18 与 1.6.2.28 另要求复刻现有麦加 911 报表。本交接包按"复刻项包含在四十张之内"编制，但这是解读。若 MOI 认为另行计数，交付量可能接近翻倍。见 HD-03 的 AS-08 与 IR-33。

### 2.2  对外数据服务是强制交付，不是预留能力（已修正）

RFP 在三处分别提出要求：1.6.2.29 要求以 Web 服务提供主要警情与告警信息，供其它 MOI 应用消费；1.6.2.31.1 要求将库与数据结构以数据服务形式暴露；1.6.2.31.2 要求为 ESB 开发适配器。

早期判断是"保留为能力但不承诺具体消费方"，理由是 DS 的大屏不交付因而没有已知消费方。这个判断混淆了"没有已知消费方"与"没有要求"。现已按必须交付项处理（REQ-API-01 至 03，决策记录 DD-24）。HLD v0.2 的 7.7 已改写为"对外数据服务与 ESB 适配器（必须交付）"。需要注意 ESB 由总包商提供，适配器的交付时间不由我方控制（AS-24、IR-26）。

### 2.3  移动应用与 RFP 存在实质差异（需商务处置）

RFP 1.3.2.12.15 明确要求信息可通过运行于 iOS 与 / 或 Android 设备的应用访问，与浏览器并列，不是可选项。早期曾将移动端列为后续阶段，理由是内政部专网不具备公网可达性导致推送不可用；该理由在详细设计阶段被推翻——系统设有 DMZ 区与短信、邮件网关，移动端本期按只读聚合管理看板交付，不使用设备推送，差异已消解（见 AS-09 与 HLD 8.4）。

这是真实的技术约束，但不能默默减项。建议在 Q&A 阶段以"请说明在专网条件下移动端告警推送的实现方式"为题提出，把约束变成双方共同认识的事实。见 AS-09、IR-32。

### 2.4  COTS 交付形态与定制开发的前提冲突（需商务处置）

RFP 1.6.1.27 要求以商用成品形态交付，1.6.1.28 要求产品上市满五年且未来五年不 EOL。本项目为定制开发。项目方针是以核心开源组件公开发布满五年应对，不另行举证产品历史。

对开发组的实际影响是一条纪律：组件与版本清单、上游发布历史与支持周期说明应当从项目第一天起按可举证的标准维护（REQ-LIC-02、REQ-LIC-07），而不是等需要举证时再补。见 AS-01。

> 从这四处得出的一个方法论结论
凭方案讨论的记忆去理解需求会漏掉硬指标。条款级的逐条复核不可省略。HD-02 追溯矩阵中"需人工复核的条款"一页保留了尚未被需求直接引用的条款，开发组应在开工前逐条确认它们确实已被领域需求覆盖。这一页不应长期保持非空。

## 3  开工前必须完成的事

下列事项不是"最好做完"，而是做不完就不应开工的部分。

| 事项 | 为什么 | 对应编号 |
| --- | --- | --- |
| 复核 HD-03 中状态为「待确认」「未确认」「待冻结」「待验证」的假设 | 把假设当事实去实现，是本项目最可能出现的返工来源 | HD-03 第 2 章 |
| 发出四组对外询问件（DS、ICP、总包商、MOI） | 答复周期长，越晚发出越可能成为进度瓶颈 | HD-03 第 6 章 |
| 确认 HD-02「需人工复核的条款」一页中的条款确已被覆盖 | 避免开发完成后才发现漏项 | HD-02 需人工复核的条款 |
| 把两项前置门写入项目计划的里程碑约束 | 数据分类政策与 DLP 登记册未经 MOI 批准，任何数据库不得进入生产与培训环境 | CN-13 · CN-14 · REQ-GOV-02 · REQ-GOV-03 |
| 把迁移方案的两个月硬期限写入项目计划 | RFP 2.7.7.3 规定合同授予后两个月内提交，且依赖对现有环境的分析已完成 | CN-15 · REQ-MIG-06 |
| 与总包商确认十七条放置与隔离要求的可满足性 | 任何一条不能满足，须重新评估服务水平承诺，而不是调整设计 | CN-25 · IR-22 · HLD 12.2 |
| 取得服务水平判定口径的书面认可 | 未事先谈定判定口径的自证等同于没有证据 | IR-21 · REQ-AVL-04 |

## 4  开发上最容易走错的六处

这些不是需求，是根据设计意图给出的实现纪律。违反其中任何一条，系统仍然能跑，但会在上线后以很难修复的方式出问题。

| 纪律 | 违反后的后果 |
| --- | --- |
| raw 层只追加、不覆盖、不修正 | 失去在数据争议中自证的能力，也失去"以后理解了可重算全部历史"的能力（DD-02） |
| mart 与 ai 只能从 core 构建，不得直接引用 raw | 同一指标出现两个数字，且两者都能自证（DD-03） |
| 展现层与外部系统一律经服务层，不得直连数据库 | 行级权限与审计留痕全部失效，性能问题无法界定责任（DD-17） |
| 未映射的代码值不得归入"其他" | 报表会安静地错掉，这是最难发现的一类缺陷（DD-06） |
| 实时状态不落库 | 会制造同一事实的第二个更快但更不可靠的版本，所有"哪个数字对"的争论都会从这里开始（DD-08） |
| 封账后的历史快照不得修改，修正进修正表 | 去年打印的报表今年重跑数值会变，报表失去公信力（DD-08 · DD-12） |

## 6  文件的维护

本交接包是受控文件集，不是一次性交付物。

假设状态变化（被证实或被推翻）时更新 HD-03，并评估对 HD-01 需求的影响。被推翻的假设不删除，改标注为"已推翻"并记录实际情况。

需求变更时同步更新 HD-01 与 HD-02，变更记录中引用相关的 AS 或 IR 编号。

架构决策变更时在 HD-04 中新增一条，不修改原决策记录——保留决策的时间序列比保持文档整洁更重要。

工作坊产出的报表与指标清单，经签署后纳入 HD-05 基线，新增项从 R-41、D-21 起编号。

HLD v0.2 已落实本次复核的更正（报表与仪表板数量、对外数据服务、受控 SQL），并补入客户反馈数据源、热点与聚集区分析、两项前置门与迁移方案硬期限、库副本交付物。
