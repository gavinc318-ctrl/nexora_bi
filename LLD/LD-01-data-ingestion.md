# 数据接入详细设计

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Detailed Design — Data Ingestion   ( LD-01 ) · 版本  v0.1 · 2026 年 9 月 · 本册定义五类连接器的运行规格、源契约的字段语义与变更流程、 · 归档库的迁移与多版本归一方法，以及校验、隔离、对账与观测的规则。

## 1  本册的范围与读法

本册细化 HLD v0.3 第 4 章，回答的是「数据怎么进来、进来的是什么、进错了怎么办」。表结构在 LD-02，指标口径在 LD-03，服务层接口在 LD-04，安全与权限在 LD-07。

接入层只有一件事是不可协商的：raw 层只做「源端原样落地」，不得在装载时应用任何版本判断、列对应关系或业务解释。所有解释性工作——版本归一、字段语义对齐、编码体系判定——一律在 staging 的 dbt 模型中完成。这条原则的价值在于代价的位置：解释错了只需 dbt run 重跑，而不必回源端重拉数据。归档十年数据重拉一次意味着重新申请权限、重新排期、重新占用他方系统的资源，那是以周计的代价（DD-58）。

## 2  源契约

### 2.1  契约是接入的唯一入口

任何一条数据进入本系统，都必须先有一份登记在 meta.source_contract 中的契约。没有契约的表、列、文件或消息一律不接，即便源端已经把它准备好了。这不是流程洁癖：契约同时承载幂等键的声明、目标 raw 表的指向与契约版本号，缺了它，重跑的幂等性与结构漂移的检测都无从谈起。

契约文件放在代码库的 contracts/ 目录，那里是权威；meta.source_contract 是部署时同步的只读副本（HLD 9.2）。改契约走发布流程：改文件、递增 contract_version、随发布制品导入。库里改不了，M-01 界面上也只能看。

### 2.2  幂等键的声明与生成

幂等键由契约声明哪几列参与，运行时以 core.nk() 把这些列的值拼成规范形式：转义反斜杠与竖线、以竖线分隔、任一列为 NULL 时直接报错而不是拼出一个看似正常的键。报错是刻意的——一个含 NULL 的幂等键会在下一次重跑时生成不同的值，静默产生重复行。

代理键由 core.sk(site_code, src_system, natural_key) 生成，是 UUID v5 的确定性哈希。同一条源记录无论装载多少次、在哪个环境装载，代理键恒等，这是全量重建可幂等的基础。禁止使用自增序列作为代理键：序列的值取决于装载顺序，重建一次就全变了。

### 2.3  每一列都要有一行登记

契约范围内的每一列在 meta.mapping_registry 中都必须有一行，状态取 verified、mapped_unverified、unknown 之一。结构漂移检测发现的新列默认落 unknown。这条规则的用意是：空白会被遗忘，未知会被统计并排期。运行监控上「unknown 列数」是一个显式指标，它不为零本身不是故障，但它长期不为零且无人处置，就是。

### 2.4  凭据不入契约

数据库口令、API 令牌、SFTP 私钥一律不写入 definition，也不写入配置文件的明文段。契约中只记录凭据的引用名，实际值由部署时注入的环境变量或密钥文件提供（部署方式见 LD-08）。理由很直接：source_contract 是一张业务人员在 M-01 界面上能看到的表。

## 3  增量接入：DS CAD 展示库（IF-02）

### 3.1  水位机制

自展示库按水位增量取数，频率一分钟。水位状态存 meta.watermark_state，每次运行读取上次的高水位、以 (高水位, 本次上界] 为窗口取数，成功后才推进水位。失败不推进——宁可下次多取一遍，也不能跳过。

本次上界不取「现在」，而取「现在减去安全边界」。安全边界的存在是因为源端事务的提交时刻晚于其时间戳：一条时间戳为 10:00:00 的记录可能在 10:00:03 才提交可见，若上界取到 10:00:00 整，这条记录就被永久跳过了。安全边界初值取 5 分钟，实际值须在联调期实测——由 DS 侧提供或由本方以重复扫描比对得出（IR-02）。

### 3.2  乱序与迟到

增量列若为业务时间（如受理时刻），则迟到数据必然存在：一条 09:58 受理的记录可能在 10:05 才写入源库，此时 10:00 的水位已经推过。因此增量列优先取源端的行更新时刻或自增标识，而非业务时间。展示库是否提供这样的列属于 IR-01 数据字典的一部分，若不提供，则必须以「业务时间减回溯窗口」的方式取数，代价是每次窗口重叠、装载量增加。

这一条在设计上不留悬念：不论采用哪种方式，重复装载都由幂等键吸收，正确性不依赖于窗口不重叠。重叠只影响成本。

### 3.3  重跑与补数

任一批次可以按 run_id 重跑，也可以按时间范围补数。两者都是幂等的：同一条源记录重复装载只会产生同一行。补数与常规运行使用同一段代码，不存在「补数专用脚本」——专用脚本是最容易与主逻辑漂移的东西，漂移之后补出来的数与日常口径不一致，且极难发现。

### 3.4  为什么基线是水位轮询而不是 CDC

展示库是 PostgreSQL，逻辑复制技术上成立，客户答复中亦有「新系统增量接入需具备 CDC 与 API 两种能力」一条。因此这里必须把选择的理由写清楚，而不是默认采用轮询。

CDC 相对水位轮询有两项优势。第一项是亚秒延迟——本系统的要求是分钟级，用不上。第二项才是关键：源端的物理删除、以及原地更新但未变更时间戳的行，水位轮询永远看不见，那一行会一直留在库里，而且不报错。这是轮询的固有缺口，不是实现质量问题。

但逻辑复制需要 DS 提供三样本方无权决定的东西：wal_level 设为 logical（改此参数要重启展示库）、一个带 REPLICATION 属性的角色与建槽权限（现在谈的是只读 SELECT 账号，见 IR-06）、以及由 DS 维护随 CAD 结构变更的 PUBLICATION。在这些未获书面确认前把 CDC 作为基线，等于把交付建在假设上。

| DS 的顾虑 | 实际风险与缓解 |
| --- | --- |
| 复制槽会撑爆源端磁盘 | 本方消费端一停（停机、网络中断、离线补丁窗口），槽即持续保留 WAL。PG 13 起可用 max_slot_wal_keep_size 封顶，超限时槽失效而非磁盘耗尽——风险由「本方停机影响 CAD 展示库」降为「本方需重新全量同步」。这条可缓解，但需 DS 主动配置。 |
| 展示库可能是物理备库 | 备库上的逻辑解码自 PostgreSQL 16 起才支持。DS 版本待确认（IR-02）。 |
| 需要引入新组件 | Debezium 一类连接器需 JVM 运行时并通常配套 Kafka，在离线环境中意味着新组件、新许可分析与新虚机。PostgreSQL 原生逻辑复制订阅可达同样目的而无此代价，故若采用 CDC 则走原生路线。 |

因此本设计的处置是：基线维持水位轮询；把逻辑复制作为备选正式列入 IR-02 向 DS 提出，不由本方代为判断对方会拒绝；并以 8.3 的滚动窗口校验补偿轮询的固有缺口，无论 CDC 谈成与否都保留（DD-61）。

把选项正式提出这一点值得单独说明。DS 很可能基于运维风险选择水位方式，但那时留下的记录是「本方提出、对方权衡后选定」；若不提，将来一旦出现漏数争议，性质就变成「没想到」。这两者在合同层面完全不同。

同批还需问清一件事：展示库若由 DS 自己的 ETL 灌入，某些表可能是整表重载。若如此，CDC 会产生海量伪变更，水位轮询同样失效——两种方案都要改（IR-02 第四问）。

## 4  轮询接入：ICP 话务（IF-03）

ICP 只提供 REST 接口，不做库复制（CN-21）。但「REST 接口」不是一条通道。读完 CloudICP V100R023C00 的 CMS Server 部分，对本方有用的面只有五组：鉴权 userauth、配置同步 synwas、历史指标 hindex、实时指标 rindex 与实时查询 real、话单报表 reports。其余各部分（Agent Server、ICS Server、ActiveX 组件）是话务台软件要调的坐席控制面，本方一个都不会用。

### 4.1  两条通道，不是一条

分界线写在接口的前置条件里：hindex 的每一个接口都要求「报表脚本已执行、话单已正确导入数据库」，而 rindex 与 real 没有这个要求。也就是说历史指标的新鲜度由 ICP 侧的报表批决定，实时指标则是即时的。这不是两种精度，是两种性质。

据此分两条通道。话单通道取原始话单，承载全部进入考核与封账的指标；实时通道取瞬时快照，只供墙面大屏与实时看板。两条通道各自独立推进，互不作为对方的补救手段。

### 4.2  话单通道（IF-03a）

接口为 POST /cmsgateway/resource/reports/vdnvoicecalldetail，返回的是 CSV 附件而不是 JSON，因此在本方按文件接入处理：落地、校验、入 raw、原文件归档（5.1 的流程）。

| 项目 | 取值与含义 |
| --- | --- |
| 过滤字段 | WAITBEGIN，呼叫进入该设备的时刻。本方水位字段取自它，不取 CALLEND。 |
| 窗口上限 | 24 小时。回补历史须按天切片，串行执行。 |
| 窗口下限 | 5 秒。 |
| 并发 | 文档明确不支持并发下载。本接口的接入并发度恒为 1，禁止在编排侧并行切片——这是接口约束，不是调优参数。 |
| 返回形态 | CSV 附件（Content-Disposition 带文件名），按 CALLEND 降序。 |
| 排序 | 降序排列不可用于增量判断。顺序是呈现属性，水位一律由 WAITBEGIN 推进。 |
| 鉴权 | 请求头 cmsgateway-token，取自 4.7 的服务账号。 |

话单共 18 列：CALLID、CALLIDNUM、CALLERNO、CALLEENO、WAITBEGIN、WAITEND、ACKBEGIN、ACKEND、CALLBEGIN、CALLEND、DEVICETYPE、DEVICENO、DEVICEIN、WAITCAUSE、RELEASECAUSE、CALLTYPE、UCENTERREASON、UCLEAVEREASON。逐列登记按 2.3 办，不另列。

### 4.3  粒度：一通呼叫对应多张话单

这是本章最要紧的一条。话单不是「一通电话一行」，而是「呼叫每经过一个设备一行」。CALLIDNUM 是同一通呼叫内部的话单序号，1 为第一张，-1 为最后一张；DEVICETYPE 标明该设备的类型（1 技能队列、2 坐席、3 IVR，另有会议、路由脚本等），DEVICENO 为设备编号——设备为坐席时即坐席工号。

所有时间字段都是相对该设备而言的：WAITBEGIN 与 WAITEND 是在这个设备上的等待，CALLBEGIN 与 CALLEND 是在这个设备上的通话；文档另给出两个恒等式：ACKBEGIN = WAITEND，CALLBEGIN = ACKEND。因此「用户等了多久」取技能队列那张话单，「接警员通话多久」取坐席那张，而「整通电话多久」必须按 CALLID 聚合——任何单独一张话单都答不了这个问题。放弃呼叫的判定同理：有队列腿而无坐席腿。

raw 层按话单行原样落，不在接入侧做通话级聚合。通话级事实是 core 与 mart 的事（LD-02）。理由与 DD-58 一致：raw 层不做解释。接入侧一旦先聚合，所有口径分歧就失去了可回溯的底稿。

呼入与呼出的判定用 CALLTYPE 的取值集合，取自文档的二次开发指南，不自行推断：呼入为 0、5、13、15、20、21、22、23、46，呼出为 7、8、9、10、12、14、16、17、41、43、44。该集合随 ICP 版本可能变化，登记在契约的 definition 中，不写死在模型里。

AS-31 已确认坐席工号与自然人一一对应、换班由接班人以本人工号重新登录。因此 DEVICENO 可直接作为接警员维度的自然键，不需要经排班表做时间段归属。这条假设若被推翻，本节的归属链路要整体改写。

### 4.4  窗口收口与迟到

按 WAITBEGIN 取窗会必然取到「半截」的话单：呼叫在窗口末尾进入设备，离开设备是窗口之后的事，此时 CALLEND 尚未产生。这不是异常，是这个水位字段的固有性质。

处置分两步。水位照常按 WAITBEGIN 推进，但每批额外回看一段时间（建议 15 分钟，实测后定），回看区间内的话单按 CALLID + CALLIDNUM 覆盖写——这两列合起来是话单的幂等键（2.2）。更长尺度的缺口由 8.3 的滚动窗口校验兜底。

跨 24 小时的超长呼叫会落进两个窗口，不须特殊处理：两张话单各自入库，通话级由 CALLID 聚合时自然合并。

### 4.5  实时通道（IF-03b）

实时通道用 rindex 与 real 两组：rindex/agent、rindex/skill、rindex/vdn 取实时指标；real/skill/currentcallstateinfo 取技能队列近五分钟的呼叫统计，real/skill/stateinfo 取技能队列明细统计，real/agent/* 取坐席状态与当前呼叫。

用途严格限定在墙面大屏与实时看板，不进入封账指标，不作为服务水平举证。理由是它只是瞬时快照：没有可回溯的明细行，两次轮询之间发生的事看不见。把它当考核依据，等于把考核结果绑在轮询时刻上。

轮询周期分开定：实时通道 5 至 10 秒，与 LD-05 的实时档一致；话单通道按 5 分钟增量加每日回扫。本册此前写的「2 至 10 秒」只适用于实时通道，对话单通道不成立——该接口窗口下限 5 秒且不允许并发，2 秒轮询既超出接口约束，拿到的也大多是半截话单。

### 4.6  参照数据与配置版本号

synwas 一组提供 VDN、坐席、坐席组、技能、技能组、被叫配置、休息原因与业务类型，是本方话务侧参照数据的来源（第 9 章）。另有 GET /synwas/versions 返回配置信息的当前版本号。

接入策略据此定为：按周期只取版本号，版本号变化才拉全量，再逐字段比对后写入 audit.reference_data_change_log。这样省掉的不是流量，是无谓的「看起来变了」——每次全量比对都会把排序或空白差异报成变更，而参照数据的变更要进 M-10 的留痕，假变更会把真变更淹掉。

### 4.7  鉴权与服务账号

POST /cmsgateway/resource/userauth/auth，以 agentId 与 password 换取 token（UUID 形态），后续请求置于 cmsgateway-token 请求头。凭据按 2.4 不入契约。

hindex、synwas 等接口要求调用者为系统管理员，或为具备质检权限的 VDN 用户。因此本方需要一个专用服务工号，并带上该权限。这是一项要向甲方与 ICP 运维方提出的具体请求，不是配置项——它涉及一个长期有效、权限高于普通坐席的账号，口令轮换在离网环境中须有既定流程。

三件事文档没有写，须向 ICP 侧问清（IR-45）：token 的有效期；同一工号的并发会话是否互斥（若互斥，有人用该工号登录就会把接入作业踢下线，这是一个会在验收演示当天发作的故障）；以及 CMS 侧是否存在调用频次限制。前两条在拿到答复前，接入作业按「token 随时可能失效」实现：遇鉴权失败即重新取 token 并重试一次，重试仍失败才告警。

### 4.8  口径来源只能单选

文档附录给出 396 个平台指标编号（IDX_xx_xx_xxx，分 VDN、IVR、Skill、Agent 四类对象，含日累计与 15、30、60 分钟趋势）。同一个话务指标，平台能出，本方也能从话单自算。两者必然有差。

规则是：凡进入考核、报表与封账的话务指标，一律由本方从话单自算；平台的 IDX 指标只用于对账与看板（DD-64）。

理由有两条。一是可回溯：客户问「这个 97.3% 是哪些电话算出来的」，平台指标答不了，而本方自算的每一个分子分母都能点到具体话单行——指标唯一口径的前提是口径可以被打开看。二是新鲜度不由本方控制：平台历史指标依赖 ICP 的报表批，而服务等级按日考核，举证材料的产生时刻不能挂在另一方的批处理上。

代价是两边数字不一致会被看见。CN-21 原本只说「对账只能与话务平台自身报表比对」，现在这句话有了具体对象：选定一组 IDX 作为对账基准，差异按 8.4 处置。对账的问题不是「谁对」，而是「差在哪一类话单上」——若差异集中在某个释放原因或某个设备类型，那是口径定义的分歧，不是数据错误。

### 4.9  四份契约

本章确定的接入落成四份契约，都在 contracts/ 目录下：if03a_icp_cdr（话单，source_id = icp_cdr_voice）、if03b_icp_agent_session（签入签出区间）、if03c_icp_agent_day（状态时长日累计）、if03d_icp_reference（参照数据，按配置版本号变更检测）。

实时通道没有契约，因为它不落 raw：实时快照由实时组件直接取用并推送看板，不进封账也不作举证（4.5）。没有落库就没有契约，这一条是刻意的——免得日后有人把看板快照当成历史数据来用。

话单契约里有三处是接口的硬约束而非可调参数，写在 window 段：窗口上限 24 小时、下限 5 秒、并发度恒为 1。枚举取值集合登记在 enums 段，值表本身在 3rd API/ 下由脚本从接口文档生成，换版本的接口文档重跑脚本并逐行比对即可——取值集合在大版本之间会变，写死在模型里就查不出来了。

## 5  文件接入与消息预留

### 5.1  文件落地（IF-05）

SFTP 目录监听，到达即处理。每批文件必须附 manifest：文件清单、行数、校验和。三者缺一不处理，并告警。没有 manifest 的文件不是「可以先试着解析看看」，而是来源不明的数据——它可能是上传到一半的文件。

处理顺序为：校验和比对、行数比对、批次级内容校验、写入 raw、归档原文件至对象存储。原文件保留，保留期按 meta.retention_policy 的 artifact 一档。原文件是唯一能回答「当时收到的到底是什么」的东西。

### 5.2  Kafka 预留（IF-04）

本期不启用，契约结构与消费者组配置预留。预留的具体含义是：连接器类型 kafka_consume 已在 CHECK 约束中、契约的 definition 形态已定义、消费位点的存放位置已在 watermark_state 中留位。启用时属于配置与联调工作，不涉及结构变更。

## 6  归档迁移（IF-01）

归档库为 Hexagon 原生的 SQL Server，读取的是 archive 副本库而非生产库（CN-36）。数据自 2016 年起，一次性全量迁入。本章是本册中最长的一章，因为这里的每一个判断都不可逆——归档迁完，源端可能就下线了。

### 6.1  连接与驱动链

微软官方的 ODBC Driver for SQL Server 是闭源专有软件，若采用，将与 RFP 2.7.3.1「全部软件采用开放许可」直接冲突，也与 LD-09「全部组件为 OSI 认可的开源许可」自相矛盾。因此驱动链一律采用开源实现（DD-52）。

两条路线在实施前期各做一次连通性与阿语字段读取验证，以实测结果择一，不靠推断。全部四项在组件清单中标注为迁移期组件：对账完成、旧系统下线、IF-01 停用之后不需要维护八年，但合同期内可能重跑迁移或复核对账，故不删除。

### 6.2  类型映射

### 6.3  时区：一个源端可能不存在的信息

REQ-MIG-08（对应 RFP 2.7.7.5）要求迁移保留原始时区。SQL Server 的 datetime 与 datetime2 不含任何时区信息，只有 datetimeoffset 含。源端实际类型待 IR-42 答复（T-30）。

若源端为无时区类型，则原始时区信息在源端即不存在，任何投标人都迁不出源端没有的东西。本方的处置是：保真源端值，另以元数据声明「该值按 +03 沙特时间解释」，并明确标注此为约定而非源端事实。这一点在迁移方案中如实写明，并在 Q&A 阶段主动向 MOI 提出，不等到验收（DD-60）。

两个分支下 core 层都统一以 timestamptz 存储并显式记下所用的时区假设，使下游口径一致。这与 DD-33 处理三套 SRID 是同一个思路：差异在入口消化掉，不留给下游。

### 6.4  字符集与 collation

阿拉伯语字段的读取正确性是本章风险最高的一项，且历来是 FreeTDS 的坑区。若源端为 nvarchar，问题较小，UTF-16 到 UTF-8 的转换路径明确；若为带阿语 collation 的 varchar，则源端存的是单字节编码，正确解码依赖于 collation 判定，判定错了不会报错，只会得到一串看似正常的乱码。

因此迁移前置一道验证：取一组已知内容的阿语记录，端到端比对源端显示值与落库后的值，逐字符核对，含变音符与不同书写形式。这道验证的结论写入迁移方案，不通过则不启动全量迁移。

### 6.5  多版本 schema 的归一

归档十年间经历数次系统升级，且按 AS-02 拿不到升级记录，版本边界只能反推。反推可能推错，因此关键不在算法精度，而在推错的代价落在哪一层——这正是 DD-58 的原则：raw 不做任何解释，版本判定与结构归一全部在 staging。

raw 的物理表数取决于归档库的实际形态，该形态待 IR-43 答复（T-31）：

版本边界的反推以 meta.value_profile 与 meta.field_availability 为输入：取值分布的突变点、列首次出现非空值的时点、列在结构中首次出现的时点，三者交叉给出候选边界。候选边界写入 meta.schema_version_registry，并标注其证据来源与置信程度——推断出来的边界与拿到升级记录确认的边界必须能分辨，否则下一个人无从判断该不该相信它。

IR-43 的第二问是这三个输入之外最有价值的一项：源端是否留存任何 DDL 变更记录、发布说明或升级工单，哪怕不完整。AS-02 假设拿不到，但那是假设而非问过。哪怕只有片段，反推就从「纯统计推断」变为「统计推断加已知锚点」，可靠性不是一个量级。

### 6.6  语义漂移：列名没变而含义变了

字段增删是好办的——列不存在就是不存在，剖面能量化。真正难的是列名未变而含义已变：优先级字段从三档改为五档，旧的「2」与新的「2」不是一回事。value_profile 能看见取值分布在某时点突变，但看不出新旧档位如何对应，那是业务知识，不在数据里。

默认不映射（DD-59）：保留原始值，加 code_era 标明所属编码体系，报表跨越边界时分段呈现、不做跨期合并。仅当业务方书面给出对照表时才按统一口径映射，并在指标定义中记录该映射的来源与生效区间。理由是三种处理里只有映射会静默改变历史数字，而它一旦写进代码就再也看不见了。

### 6.7  归一化的范围

归一化只覆盖当前指标口径反查出的字段闭包，不覆盖全表。归档十年间系统功能持续增加，早期尤甚，而客户判断早期新增的多数字段业务上并不重要、真正需要动用的概率很小。为它们建归一模型是把成本花在概率很小的用途上，且模型还要维护八年。

闭包外的字段原样保留在 raw、不解释不映射，在 meta.mapping_registry 中状态记为 unknown 而非留空，note 注明「早期功能字段，当前无指标依赖」。

但 meta.field_availability 的剖面覆盖全部列，而不只是闭包内的列。这一条是刻意加的：「等真要用了再去研究」将来能不能做成，取决于那时候还剩下什么。剖面是一次性且低成本的，有了它，三年后有人问「2017 年到底有没有某字段、填了多少」能当场回答，而不必重新扫十年数据、重新申请归档库权限、重新找当年的人。我们现在欠未来的不是归一化，是可追溯性——归一化可以省，可追溯性省不得。

### 6.8  可用性剖面与指标起始可用年份

迁移期做一次全量字段可用性剖面，按（字段, 年份）统计行数与非空数，并区分「列在该年结构中不存在」与「列存在但为空」。前者是 schema 版本边界的硬证据，后者是业务采集习惯问题，后者可能可补救、前者不可。混作一谈就把最强的线索丢了。

阈值入表不入代码（meta.availability_threshold）：「多少填充率算可用」是业务口径，客户可能认为 80% 已足以支撑趋势分析。指标继承其全部输入字段中最差的状态并记下造成该状态的字段名，结果写入 meta.metric_availability，由服务层在每次查询时读取。

这张表必须机器可读，不能只作为 Word 交付物。若只写在对账报告里，客户看到的还是空白报表——没人会去翻附件第 12 页（DD-57）。同一份数据另出静态对照表，随迁移对账报告交付，并附一份「未归一字段清单」，写明哪些字段留在 raw 未解释、各年填充率多少。后者既是诚实交付，也是将来那次「研究」的入口。

### 6.9  分批与断点

十年数据按年分批、按实体分组，每批独立提交、独立对账、独立记录 run_log。任一批失败只重跑该批。禁止一次性事务包住全部迁移：一是长事务会拖垮源端与目标端，二是失败后无从判断做到了哪里。

每批完成后立即对账，不等全部迁完。晚发现一批的错，后面所有批可能都带着同样的错。

## 7  校验、隔离与放行

### 7.1  批次级校验，整批拒绝

校验在批次级进行，不在行级。一批数据只要有一条不满足契约声明的期望，整批进隔离区，不做「好的放行、坏的隔离」的部分处理。

理由是部分放行会产生一种最难排查的状态：库里有这批数据，但不完整，而指标照常算出了一个数。这个数不会报错，只会偏。整批拒绝虽然粗，但它的失败是可见的。

### 7.2  隔离区与待澄清队列

隔离的批次原样保留在隔离区，附失败原因、批次标识与运行标识。M-03 界面可查看、放行或丢弃，两者都留审计。放行前必须先解决原因或显式记录「已知并接受」，不允许无理由放行——无理由放行的批次三个月后没有人能说清当时为什么放。

待澄清队列按影响行数与受影响指标排序，因为队列长了就没人看了，排序决定了有限的注意力花在哪里。

## 8  对账

### 8.1  归档逐批对账

每批迁移完成后立即对账，三项：行数、关键度量的合计、按月分布。三项都通过才算该批完成。

行数比对最基础，但单靠它不够——它查不出内容错位。度量合计能查出数值列的整体偏移。按月分布能查出时间字段的解析错误，这类错误在行数与合计上都看不出来，但一画分布图就很明显：某几个月凭空多出数据、另几个月归零。

### 8.2  持续源日对账

DS CAD 展示库与 ICP 每日对账一次，在日切封账之后。对账口径与归档相同，差异写入对账结果表，超阈值告警。

对账的对象是源端，不是上一次的自己。与上次结果比对只能发现变化，发现不了系统性偏差——若某个映射从第一天起就错了，与自己比永远是一致的。

### 8.3  滚动窗口校验：轮询缺口的补偿

水位轮询看不见源端的物理删除，也看不见未变更时间戳的原地更新（3.4）。8.1 与 8.2 的对账查不出这两类问题——它们比的是总量与分布，而这两类变更恰恰不改变本方已有数据的任何统计特征，只是让本方的数据与源端不再一致。

因此增设滚动窗口校验，每日一次，在日切封账之后：取近 30 天，按日分区逐日比对源端与本方的行数与关键列哈希值。

实现方式需要说明清楚，因为「两侧各自计算」这句话容易被误解为要 DS 部署一个程序——那样这个方案根本不成立。实际是：本方以只读账号向源库发一条聚合 SELECT，计算在 DS 的 PostgreSQL 引擎内完成，返回的是每天一行的（日期, 行数, 哈希）。DS 不需要安装或运行任何东西，数据本体不出源库，回传的只有聚合值。

成立的前提是两侧的序列化规则完全一致，而默认的类型到文本转换并不可靠。实测：numeric 的裸 ::text 转换保留各自的标度，0.5 与 0.500 是同一个值却得到两种文本，哈希随之不同——数据完全一致，哈希就是对不上，而这类假差异查起来极费时间。因此序列化规则由契约固定，不依赖任何默认行为：

| 规则 | 理由 |
| --- | --- |
| 数值一律 to_char 显式定标度，不用 ::text | 源端与本方的列定义标度可能不同，裸转换会产生假差异。 |
| 时间戳一律 AT TIME ZONE UTC 后按固定格式串 | 不依赖会话的 TimeZone 与 DateStyle。实测把 DateStyle 改为 SQL, DMY 后哈希不变，只有分组标签的显示变化——因此客户端比较的是日期值而非其文本形式。 |
| NULL 用 \N 哨兵 | 空串与 NULL 必须能分辨，否则一个被清空的字段看起来仍然一致。 |
| 列顺序按契约声明，而非表定义顺序 | ALTER TABLE 会改变表定义顺序，届时哈希全线不一致，而数据没有任何问题。 |
| 聚合用与顺序无关的求和 | md5 取两段 32 位切片各自求和，等效 64 位。不用 string_agg——它需要排序且内存随行数线性增长，在源端跑大分区会很难看。 |

本方侧对 raw 的副本执行同一段序列化与聚合逻辑，代码共用，不写两份——两份实现迟早会漂移，而漂移之后所有的差异都是假的。

负载须与 DS 写入接口协议：这是一次日分区的顺序扫描，时段、频率与并发上限都要谈定（IR-06 已在询问负载约束）。若 DS 不接受每日全窗口扫描，退路按优先次序为：降频至每周、缩短窗口、只对关键列子集计算哈希。三者都损失覆盖度，但都强于没有。

同一方法可用于 8.1 的归档逐批对账，T-SQL 侧改用 HASHBYTES。但序列化规则须在 SQL Server 上重新逐项验证，不得假定两个引擎的默认文本表示一致——上面 numeric 的例子在同一个引擎内就已出现，跨引擎只会更多。

| 比对结果 | 含义与处置 |
| --- | --- |
| 行数与哈希均一致 | 该日分区一致，无动作。 |
| 行数一致、哈希不一致 | 存在原地更新且水位未捕获。定位到具体行后按幂等键重取该日数据。 |
| 本方行数多于源端 | 源端发生了物理删除。这是最需要显式处置的一类：须先确认 CAD 的删除语义（业务撤单还是数据修正），再决定本方是同步删除还是标记失效——两者对历史指标的影响完全不同，不能由技术侧径自决定。 |
| 本方行数少于源端 | 漏数。查水位、批次边界与隔离区，通常是某批仍在隔离而未被注意到。 |

窗口取 30 天是一个权衡：足以覆盖绝大多数迟到与更正，又不至于让每日扫描的代价过大。窗口长度入配置而非写死，实施期按实际负载调整。

这道校验独立于 CDC 是否采用：若 DS 同意逻辑复制，它是对 CDC 链路本身的交叉验证；若维持水位轮询，它是唯一能发现上述两类变更的手段。两种情况下都保留（DD-61）。

需要说明它不是万能的：它只覆盖滚动窗口内的分区。窗口之外的历史数据若在源端被修改，本方不会发现。这是一条已知边界，写入迁移与运维文档，而不是留给使用者自行想象。

## 9  参照数据维护

本系统没有人工录入的业务数据源。原先设想的三类旁路数据在逐项核实后全部清空：排班计划改为派生时间带（DD-53）、勤务级别保留 CAD 接口为非必选项且不做人工维护（DD-54）、复核与质检属 IRMS 不在本系统范围（DD-55）。M-10 剩下的只是参照数据维护——是配置，不是数据源。

### 9.1  M-10 维护的内容

### 9.2  双语译名随源端改名失效

人工译名描述的是他方系统里的对象。源端一旦改名，旧译名可能只是措辞变化，也可能意味着单位合并、拆分或改隶属，而报表上不会有任何迹象。

因此译名挂在自然键上（译的是实体，不是 SCD2 的某个版本），并记下确认当时源端的原文。源端现值与之不符即置 pending_reconfirm，展现层回落显示源端原文而非可能已失效的旧译名，M-10 列出待办（DD-56）。

不做任何名称规范化或格式差异过滤。客户答复改名频率为数年一次，为降低一个数年一遇的误报而引入规则表，成本超过收益，且规则本身在交接时还要解释和维护。存原文而非哈希，是因为待办界面要能并排显示「确认时源端是这个、现在是这个」，让确认者自己判断这是改措辞还是实体变了。

### 9.3  逐字段留痕

M-10 的全部维护动作逐字段写入 audit.reference_data_change_log：目标表、业务键、字段名、旧值、新值、操作人、时间、原因。参照数据不经 raw 层，没有 run_log 血缘，此表是唯一的追溯来源。改错一行班次窗口就能改变一批报表数字，而这个动作本身不留痕的话，事后无从查起。

## 10  运行与观测

### 10.1  运行日志

每一次连接器运行写一条 meta.run_log：运行标识、源标识、窗口起止、行数、结果、耗时、错误摘要。这张表同时是 M-01 界面的数据来源与服务水平举证的一部分。

运行日志只增不改。重跑产生新的 run_id 而不是覆盖旧记录——覆盖之后就无法回答「这批数据重跑过几次、为什么」。

### 10.2  告警口径

告警经统一投递服务发出，短信与邮件两个通道，网关由总包商运维。告警内容不含数据本体，只含定位信息——告警会走出内网，走的是 DMZ。

### 10.3  补数与重跑

补数与常规运行共用同一段代码，按时间范围触发。全部装载路径幂等，因此补数不需要先删除再插入，这一点尤其重要：先删后插在失败时会留下一个数据缺失的窗口，而这个窗口的存在不会有任何提示。

| definition | jsonb。连接参数、幂等键列清单、增量列、分页与限流参数等按连接器类型各有其形。凭据不入此字段（见 2.4）。 |
| enabled | 启停。停用的契约保留而不删除，否则历史 run_log 的外键失去指向。 |

| 状态 | 含义与处置 |
| --- | --- |
| 正常推进 | 本次窗口取数成功、校验通过、写入 raw 完成，水位推进至本次上界。 |
| 失败不推进 | 任一环节失败，水位保持不变，下次运行自动覆盖同一窗口。因幂等键存在，重复装载不产生重复行。 |
| 人工回拨 | 发现某时段数据有误需重取时，由 M-01 界面回拨水位。回拨是一次带审计的动作，记录操作人、回拨前后的水位与原因。 |

| 事项 | 处置 |
| --- | --- |
| 分页 | 按游标分页而非按页码。页码分页在数据持续写入时会漏记录：第 2 页取数时若第 1 页新增了一条，原第 20 条被挤到第 21 位而从未被读到。 |
| 限流 | 契约中声明每分钟最大请求数，运行时自行限速，不依赖对方拒绝。被对方限流视同失败，进入退避。 |
| 失败退避 | 指数退避，初值 2 秒、上限 5 分钟。连续失败超过阈值转告警，但不停止轮询——话务数据的中断时间直接进入服务水平举证。 |
| 时钟偏差 | 记录本方接收时刻与 ICP 返回时间戳的差值，写入 run_log。偏差本身不影响装载，但它是排查「数字对不上」时的第一个要看的东西。 |
| 重复投递 | 同一条通话记录可能被返回多次。由幂等键吸收，不做去重逻辑——去重逻辑需要状态，状态就是新的故障点。 |

| 状态 | 判定与报表行为 |
| --- | --- |
| available（非空率 ≥ 95%） | 可直接出数，报表不加提示。 |

| unavailable（< 5% 或列不存在） | 报表显示「该时段源端无此数据」并指名限制字段，既不显示空白也不显示零。 |

| 校验类别 | 内容 |
| --- | --- |
| 结构 | 契约声明的列是否都在、类型是否可转。新增列不算失败，记为 unknown 进 mapping_registry。 |
| 键 | 幂等键各列是否非空、批内是否唯一。 |
| 值域 | 契约声明的枚举、范围、非空约束。值域外的取值同时写入 value_profile，因为它可能是源端新增了编码而非数据错误。 |
| 量 | 本批行数与历史同期的偏离度。零行与暴增同样可疑：零行可能是源端故障，也可能是水位取错。 |
| 引用 | 外键指向的维度成员是否存在。缺失不一定是错误——维度可能晚到，故此项失败进待澄清队列而非直接隔离。 |

| 差异类型 | 处置 |
| --- | --- |
| 行数差 | 先查水位与批次边界，再查隔离区。多数行数差是某批仍在隔离而未被注意到。 |
| 合计差 | 定位到列，再定位到行。若源端在对账窗口内仍有更新，属正常现象，须以源端快照时点为准重新比对。 |
| 分布差 | 优先怀疑时间字段的类型映射与时区处理，见 6.2 与 6.3。 |
| 持续存在的小差异 | 不得以「在容差内」结案。写入待澄清队列并定期复看——稳定的小差异通常意味着一条稳定的错误规则。 |
