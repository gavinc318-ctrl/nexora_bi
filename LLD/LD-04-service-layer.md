# 服务层与接口详细设计

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Detailed Design — Service Layer and Interfaces   ( LD-04 ) · 版本  v0.1 · 2026 年 9 月 · 本册定义服务层的出口路径与接口契约：查询 API、记录检索、受控 SQL、 · 实时推送、投递服务、对外数据服务与 ESB，以及 AI 集成的四个接口。

## 1  本册的范围与读法

本册细化 HLD v0.3 第 7 章，回答的是「数据以什么形式离开这个系统、谁能拿到、拿到的东西附带什么声明」。指标怎么算在 LD-03，权限怎么判在 LD-07，界面怎么用这些接口在 LD-05。

服务层是本系统对外访问的唯一出口。展现层、移动端、AI 包、ESB 调用方、外部系统一律经服务层，任何组件都不得直连数据库。这条约束若不成立，LD-07 的三层权限与本册的审计留痕将全部失去意义——绕过服务层的一次查询，既不受字段裁剪与行过滤约束，也不会在审计里留下任何痕迹。因此提出直连需求的场景必须走变更评审，而不是由实施人员就地开个只读账号了事。

## 2  出口路径的全集

把出口路径列全，是本册第一件要做的事。原因在 LD-07 第 3 章已经说过：权限必须在每一条出口上生效，漏掉一条，前面所有的权限设计就都只是装饰。因此这里不按「主要接口」列举，而是穷举——包括那些以系统身份运行、没有人在屏幕前的路径。

最后两条值得说明为什么列在这里。受控 SQL 与库副本交付都不是「接口」，但它们同样是数据离开系统的方式，而且是权限约束最弱的两种。把它们和 REST 接口并列在同一张表上，是为了让「哪些路径能拿到数据」这个问题只有一个答案来源。

## 3  查询 API

### 3.1  语义：按指标查，不按表查

查询 API 的入参是指标编码、维度组合、过滤条件、时间范围与时间粒度，不是表名与列名。指标定义由语义层解析为 SQL，调用方看不到也不需要看到底层表结构。

这样设计的代价是灵活性——调用方不能随便组合任意两列。收益是口径唯一：同一个指标编码在门户、报表、移动端、对外接口上解析成同一段 SQL，不存在「前端自己拼了一个稍有不同的算法」这种问题，而后者是 BI 系统中数字对不上的最常见成因。

### 3.2  执行位置与保护

查询一律在分析副本执行，只读，任何情况下不触碰主库。这不是性能优化，是隔离：一条写错的分析查询不应当有能力影响接警业务所依赖的写入路径。

### 3.3  缓存键必须含完整权限上下文

缓存键由指标、维度、过滤条件、时间范围、口径版本、封账状态，加上调用者的完整权限上下文共同构成。权限上下文包括角色、字段可见性白名单的指纹，以及部门行过滤的取值。

三项缺一不可，而且这一条是被修正过的：设计中曾只把字段白名单指纹纳入缓存键，那样只防住了列泄漏，防不住行泄漏——A 部门的调度员查完之后，B 部门的调度员命中同一份缓存，看到的是 A 部门的行（DD-50）。字段与行是两个独立的维度，缓存键必须同时覆盖。

随之而来的是缓存命中率下降，因为不同部门的同一查询不再共享缓存。这是正确的代价：一个会串数据的缓存，命中率再高也没有意义。

### 3.4  四个响应元字段

每一个响应都携带四个元字段，它们不是调试信息，是数据本身的一部分。对外调用方（IF-33）同样收到，因为口径声明对机器调用方比对人更重要——人还会看报表脚注，机器不会。

查询范围超出 meta.metric_availability 的可用年份时，不返回空结果，而是在响应中明示「该时段源端无此数据」并指名限制字段，由展现层原样呈现（LD-01 6.8 · DD-57）。空结果与「源端没有这个字段」在数字上都是零，含义却完全不同，而使用者无从分辨——这正是必须由服务层显式区分的理由。

## 4  记录检索

RFP 1.6.2.7 要求按记录检索——按案件号、电话号码、时间范围、地点查到具体的那一条，而不是聚合出来的数。这是一个独立组件，不是查询 API 的一个参数（DD-34）。

把它单列的理由是两者的性质完全不同。查询 API 面向聚合，落在 mart 层，结果集小，缓存有效；记录检索面向个体，落在 core 层的事实表，要走分区裁剪与精确索引，且返回的是包含个人信息的明细。两者的权限判定、审计粒度、性能特征、缓存策略没有一项相同，硬塞进同一个接口只会让两边都别扭。

## 5  实时推送与投递

### 5.1  实时推送网关（IF-31）

实时状态服务以独立连接池短周期拉取源系统的当前状态，在内存中维护「此刻」视图并计算变化量，经 WebSocket 网关按角色与部门过滤后推送。两个实例之间用 PostgreSQL 的 LISTEN / NOTIFY 保持一致，不为此引入新的中间件。

这条路径不写数据库。实时状态是对另一个系统的观测，不是本系统自己的记录；落库会制造出同一批事实的第二个版本——更快，但更不可靠——而所有关于「哪个数字是对的」的争论都会从这里开始。因此它只存在于内存中，随进程结束而消失，也因此它不能用于统计与考核。

### 5.2  断线重连：回送快照而非补发事件

客户端保存收到的最后一个序号，重连时提交该序号，网关回送一份完整的状态快照，而不是补发期间的全部事件。一块中断两小时的大屏在一次往返后即恢复正确，无需人工干预。

补发事件的方案需要网关为每个客户端保留事件队列，队列长度无上界（谁也不知道一块大屏会断多久），且重放期间的顺序与幂等都要处理。回送快照把这些问题一次性消掉，代价只是一次全量传输。对于「此刻视图」这种本来就只关心当前值的数据，历史事件没有保留价值。

权限在订阅建立时判定，并在每次推送时复核。只在建立时判定是不够的：一个长连接可能存续数小时，期间用户的部门归属或角色可能已经变更，而按 LD-07 的规则权限判定按当前状态而非订阅时状态。

### 5.3  投递服务：以系统身份运行的那条路径

报表订阅与告警分发由统一投递服务承担：两类内容（报表产物、告警消息）乘三条通道（邮件网关、短信网关、门户内消息）。订阅由人配置，但执行时没有人在屏幕前——它以系统身份运行。

这是全系统最容易漏掉权限的一条路径，因此明确写死：报表内容按订阅者本人的权限上下文渲染，而不是按配置者的、也不是按某个服务账号的。一个部门主管订阅了一张全局报表，他收到的邮件里只应有他有权看到的那些行与那些列。

### 5.4  媒体服务

对象存储不对客户端直接暴露。媒体服务负责鉴权、签发短时效访问凭证、记录访问留痕。现场照片、报表产物与 AI 导出文件均通过该服务访问。

凭证短时效且一次性，过期即失效。理由是一个长期有效的对象存储直链一旦出现在浏览器历史、邮件正文或聊天记录里，就脱离了本系统的一切控制。

## 6  受控 SQL

受控 SQL 是唯一绕过指标语义层、直接向分析副本提交 SQL 的通道。它的存在理由是现实的：总会有一次分析是预置指标覆盖不到的，而没有这个通道，人们就会去要一个数据库账号——那才是真正失控的开始。

### 6.1  只给自然人，不给系统

受控 SQL 只授权给自然人，不授权给任何系统或服务账号。系统之间取数一律走服务层接口（DD-51）。

这一条在讨论中曾经放宽过：一度考虑允许把最高权限角色授予一个系统主体，由调用方自负数据安全。放弃的理由是责任无法落地——「调用方负责」需要有一个能负责的对象，而一个服务账号不会为泄漏承担任何后果，它背后的责任人也不会自动出现在任何一张表里。因此 meta.sql_grant 的表结构上就写死了这一点：responsible_party 为必填，且 directory_verified 有 CHECK 约束、默认值缺省即无法插入，迫使授权动作显式声明「已核实该主体在目录中存在且为自然人账号」这件事做过了。

## 7  对外数据服务与 ESB（IF-33）

RFP 在三处分别要求对外提供数据，因此这是必须交付项而非可选能力。鉴权采用 OAuth2 客户端凭证，路径版本化。

对外调用方同样收到四个响应元字段。这既是数据质量的声明，也是本方指标口径的技术表达——一个机器调用方拿到未封账的当日临时值却不知道它是临时值，比人拿到更危险，因为它不会犹豫。

路径版本化的含义是口径变更不修改既有版本的行为：新口径开新版本路径，旧版本按约定期限并行,到期下线并提前通知。对外接口一旦被别的系统集成，就不再是本方可以单方面改动的东西。

## 8  AI 集成的四个接口

AI 能力由联合体内的 AI 包实现，本方交付集成接口（DD-28）。四个接口分属两个方向，边界必须清楚：本方供数与承载回流，不做推断；AI 包做推断，不直接读库。

### 8.1  为什么 AI 包不生成 SQL

让模型直接生成 SQL 看似省事，实则把三件事一起交了出去：口径的正确性、权限的完整性、以及查询对数据库的影响。生成的 SQL 绕过指标语义层就绕过了口径唯一性，绕过服务层的过滤下推就绕过了权限，而一条模型生成的全表扫描没有任何东西拦得住它。

因此 IF-38 提供的是语义目录加结构化查询：AI 包表达「要什么」，本方决定「怎么取」。这与 DD-51 拒绝把受控 SQL 开给系统主体是同一条推理。

### 8.2  MCP 绑定

IF-38 以 REST-JSON 为第一绑定，MCP 为第二绑定，二者语义等价、共用同一套语义目录与权限下推，不是两套实现（DD-29）。MCP 规范版本冻结在 2026-07-28，写入组件清单。

MCP 作为可选增补项的判断依据是：它降低 AI 侧的接入成本，但本方的交付不依赖它成立。若 AI 包选择 REST 绑定，MCP 绑定不启用亦不影响任何验收项。

## 9  移动端对外面（IF-40）

移动端为只读聚合看板，形态为原生薄壳加内嵌页面。它不是接警员与调度员的作业工具，因此不做记录级下钻——记录检索接口对移动端令牌一律拒绝，这是接口层的硬拒绝，不是界面上不放入口。

## 10  错误与契约稳定性

### 10.1  错误必须可分辨

接口错误的分类不是工程洁癖，而是因为「没有数据」在数字上永远是零，而它可能出自五种完全不同的原因。使用者无从分辨，只能由服务层显式区分。

第三种情形值得单独强调：映射不上时静默返回空是最难发现的一类缺陷——使用者看到的是「本部门今天没有警情」，而事实是他的部门编码对不上（T-27）。

### 10.2  契约稳定性

OpenAPI 规范为接口的权威定义，随版本发布。对内接口（展现层）与对外接口（IF-33、IF-37 至 IF-39）的变更纪律不同：前者可与前端同步发布，后者按 7 章的版本化规则处理。

响应中新增字段视为兼容变更，删除或改变既有字段语义视为不兼容变更。这条界线要写进接口文件，因为「我们只是把某个字段的含义调整了一下」在集成方那里等同于一次故障。

| responsible_party | 责任方。「数据安全由调用方负责」须有对象，否则出事无从追责。 |
| allow_export | 导出单独控制、单独记审计、可单独关闭——一旦导出，责任边界就延伸到了个人电脑上。 |
| daily_query_quota · max_rows · statement_timeout_ms | 配额、行数与超时。三者都有默认值，不允许无限制授权。 |
| expires_at · is_revoked | 到期与吊销。长期有效的高权限授权最终都会变成没人记得的授权。 |
