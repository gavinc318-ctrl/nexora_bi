# 安全与权限详细设计

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Detailed Design — Security and Access Control   ( LD-07 ) · 版本  v0.1 · 2026 年 9 月 · 本册定义身份（经 AD FS 代理）、三层权限模型、出口路径的覆盖要求、受控 SQL 的授权、 · 审计留痕，以及脱敏与匿名化规则。

## 1  本册的范围与读法

本册细化 HLD v0.3 第 10 章。权限的结构性决定已在 HD-04 中定稿，本册回答的是「怎么实现、在哪里实现、漏了会怎样」。

有一条贯穿全册的判断：本系统的权限缺陷几乎都不报错。越权返回的是多几列数据或多几行数据，功能完全正常，除非专门比对否则看不出来。因此本册的重点不在于列出规则，而在于列出规则容易失效的位置。

## 2  三层权限

权限有三层，各管一件事，不可互相替代。

| 层 | 管什么 | 配置位置 |
| --- | --- | --- |
| 角色 | 能进哪些界面、能用哪些功能 | 四角色，来自 MOI 目录（HLD 10.2） |
| 字段级可见性矩阵 | 能看到哪些列 | meta.field_visibility，在 M-06 维护（DD-35） |
| 部门级行过滤 | 能看到哪些行 | 按派驻警种，调度员与主管受限，接警员与管理员不受限（DD-41） |

### 2.1  角色

| 角色 | 界面范围 | 是否受部门过滤 |
| --- | --- | --- |
| 接警员 | 与本人相关的话务与警情视图、个人绩效 | 否（接所有来电） |
| 调度员 | 警情处置视图与资源状态 | 是，仅见本警种的派警单与出警单 |
| 主管 | 业务报表、仪表板、大屏、班组与人员绩效 | 是，按派驻警种 |
| 管理员 | 全部业务视图与 M-01 至 M-11 | 否 |

接警单在派警单的上一层，对全部角色可见——完全屏蔽会使调度员看到的警情量与实际不符，跨部门协同报表 R-19 也无从做起。受限的是派警单及其下游的出警单与反馈单。

### 2.2  字段级可见性矩阵

矩阵的结构由本方交付，默认取值由 MOI 的数据分类政策确定（CN-13 前置门）。下表是本方提交给 MOI 的起草值，未获批准前不作为实现依据。

| 字段 | 起草的可见范围 | 理由 |
| --- | --- | --- |
| 报警人号码 | 全部角色默认不可见，需单独授权 | 本系统是分析系统而非作业系统。接警员在实时接警时看到的号码来自 CAD 与话务平台，不经本系统。默认关闭可显著降低数据分类政策的审批难度 |
| 警情描述原文 | 主管可见；调度员限本警种；接警员与管理员默认不可见 | 跨部门协同与异常事件分析需要原文；复核与质检本身属 IRMS，不在本系统范围（DD-55）；管理员多为 IT 人员，按多数合规框架不应看业务敏感内容 |
| 精确坐标与地址文本 | 调度员限本警种、主管可见；其余默认不可见 | 处置与热点分析需要；聚合后的网格数据不受此限 |
| 处置反馈正文 | 调度员限本警种、主管可见 | 同上 |
| 人员姓名（警员与坐席） | 主管与管理员可见；调度员限本警种 | 绩效报表需要；跨部门的个人绩效不属任何人的工作范围 |

两条实现纪律：裁列必须在服务层构造查询时完成，不可见字段根本不进入结果集——前端隐藏时数据已经传到客户端，等同于未做控制；导出的白名单独立于查询白名单配置，且默认更严，因为导出之后数据落在个人电脑上，不再受任何控制。

### 2.3  部门级行过滤

过滤条件来自身份系统的当前部门，作用在 fact_dispatch_order 及其下游。三条实现要点：

| 要点 | 说明 |
| --- | --- |
| 编码以 CAD 的处置单位编码为权威 | 身份侧的部门必须映射到有效编码。映射不到时拒绝放行并告警，不得静默返回空结果——空结果会让用户以为今天没有警情，而不是以为自己没有权限 |
| 权限按当前，统计按当时 | 权限判定用当前部门，调岗后不再可见原部门数据；统计口径仍关联当时的维度版本（DD-12）。两者正交，实现时不得混用 |
| 过渡期的数据来源 | 部门组可作为声明随令牌传出之前，映射表在 M-06 本地维护（IR-39）。目录侧就绪后切换为以目录为权威，映射表退化为对照（见 6.6） |

## 3  出口路径 × 权限层：必须是笛卡尔积

权限有三层，数据离开系统的出口有六条。任一格子漏掉，整个控制在那条路径上等同于未做，而且不报错。

| 出口路径 | 谁在调用 | 最易出错之处 |
| --- | --- | --- |
| 查询 API | 门户、仪表板、大屏 | 缓存串号，见第 4 章 |
| 记录检索 | 门户 | 返回字段未按矩阵裁列；条件集配置绕过白名单 |
| 导出 | 门户 | 沿用查询白名单而非导出白名单 |
| 报表订阅分发 | 系统身份的异步任务 | 最容易遗漏的一条：任务以系统身份运行，须显式携带订阅人的部门与字段上下文 |
| 对外数据服务 IF-33 | ESB 与外部应用 | 客户端凭证须映射到角色，受同一矩阵约束 |
| MCP 绑定 | 外部 AI 框架与 ML 平台 | 同上；且返回须携带四个元字段 |

> 报表订阅分发值得单独说    它是唯一以系统身份而非用户身份运行的出口。功能测试会验证「报表能生成」，不会验证「以谁的权限生成」——因为两者都能生成一份看上去正常的报表。LD-10 的 TC-DISC-01 专门测这一条：以民防调度员为订阅人生成跨警种报表，检查产物是否只含民防的数据。 凭方案讨论的记忆去理解需求会漏掉硬指标。条款级的逐条复核不可省略。HD-02 追溯矩阵中"需人工复核的条款"一页保留了 32 条尚未被需求直接引用的条款，开发组应在开工前逐条确认它们确实已被领域需求覆盖。这一页不应长期保持非空。

## 4  缓存与权限上下文

DD-35 原本规定缓存键须包含字段白名单指纹。该规定只挡住了列的串号，挡不住行的：民防的调度员与警察的调度员角色相同、字段白名单完全相同，但可见行不同。若缓存键不含部门，第二人的查询会命中第一人的缓存，直接看到对方警种的数据。

因此改为：缓存键由完整的权限上下文哈希构成，至少含角色、部门、字段白名单指纹与查询指纹四项（DD-50）。实现上取权限上下文对象的整体哈希而非逐项拼接——将来权限模型再增维度（按辖区、按时间范围授权）时不会重演本次遗漏。

权限变更时按主体使相关缓存失效。矩阵或部门映射一改，旧缓存立即作废，不等自然过期。

## 5  受控 SQL 的授权

RFP 1.6.2.15 要求可使用通用 SQL 生成简短报表。这是「不绕过语义层」的唯一例外，因此它的授权方式与其它权限不同。

| 规则 | 说明 |
| --- | --- |
| 只授予自然人 | 服务账号不得出现在授权名单中。系统所需的一切访问，服务层的查询 API、记录检索、对外数据服务与 MCP 绑定均已提供，且那些路径自带字段矩阵、部门过滤与审计。给系统开自由 SQL 等于在唯一出口旁边另开一扇门，无收益只有风险（DD-17 · DD-51） |
| 按主体显式授权 | 独立于四角色，在 M-06 维护。授权前须核实主体在 MOI 目录中存在且为自然人账号；撤销即时生效，变更写审计 |
| 责任方必填 | 被授权人在其范围内可见全量数据，该范围内的数据安全由调用方负责。这是组织责任的显式转移，没有责任方就无从追责 |
| 授权名单须经 MOI 批准 | 「谁能看全量数据」不是本方可单方面决定的技术选择，须写入我方提交的数据分类政策输入稿 |
| 技术护栏与授权无关 | 只读、仅走分析副本、强制超时、结果集上限一律保留。它们防的不是越权，是一条失控查询打穿 95% 亚秒的承诺 |
| 导出单独控制 | allow_export 默认为假，单独记审计、可单独关闭 |

实现上，meta.sql_grant 的 directory_verified 列无默认值且带 CHECK 约束，插入时必须显式声明为真。这挡不住有人硬填，但挡得住顺手把一个服务账号填进去——授权时必须停下来想一次这是谁。

## 6  身份：经 AD FS 做身份代理

### 6.1  MOI 已有的身份基础设施

MOI 已部署并购置了完整的微软身份栈：域控 MGMTADDS01 / MGMTADDS02（AD DS，用户与组的权威）、联邦服务 MGMTADFS01 / MGMTADFS02（AD FS，对外发令牌）、证书颁发机构 MGMTADCS01（AD CS，内部 CA）。本系统不新建任何用户目录，也不复制一份用户数据（IF-35）。

三者各管一段，不要混淆：AD DS 是「谁是谁、属于哪个组」的权威；AD FS 把这件事变成一张可被外部应用校验的令牌；AD CS 签发证书，第 7 章的 sslmode = verify-full 与门户的服务端证书都来自它。

### 6.2  为什么是身份代理，而不是让 Keycloak 直连 AD 做 LDAP 联邦

Keycloak 有两种对接方式。一种是 User Federation，即 Keycloak 以 LDAP 直连域控，用户在 Keycloak 的登录页输入 AD 口令，Keycloak 拿这对凭据去域控做 bind。另一种是 Identity Brokering，即把登录重定向到 AD FS，用户在 MOI 自己的登录页完成认证，Keycloak 只接收并校验 AD FS 签发的令牌。

本方案取后者。理由不是偏好，有四条：

一、本方永不接触 AD 口令。LDAP 直连意味着用户的域口令要经过我方的登录页与我方的进程内存——这在任何一次安全审查中都是要重点解释的事，而代理方式下这个问题根本不存在。

二、MFA 与条件访问留在 MOI 手里。MOI 若已启用或将来启用多因子、设备合规、登录位置限制等策略，这些策略作用在 AD FS 的认证环节；走代理，它们自动生效且与 MOI 其它系统一致。走 LDAP bind，这些策略全部被绕过——而「绕过」这件事通常要到审计时才被发现。

三、口令策略的语义不落在我方。锁定阈值、过期提醒、首次登录必须改密、禁用账号的即时生效——LDAP bind 方式下这些都要我方在登录页上逐条复刻，复刻得不对就成了安全缺口或支持工单。

四、不需要一个有目录读权限的服务账号长期存在。LDAP 联邦要一个能读目录的绑定账号，它的口令要我方保管、轮换，且一旦泄露，影响面是整个目录而不只是本系统。

代价要如实记下：身份链路多了一跳，AD FS 不可用时本系统无法登录（与 MOI 其它依赖 AD FS 的系统同时不可用，属平台级故障而非本系统故障）；并且令牌签名证书的轮换成为一项长期运维义务，见 6.5。该选择记为 DD-72。

### 6.3  身份链路

浏览器 / 移动端 → 门户或服务层 → Keycloak（OIDC 提供方）→ AD FS（上游 IdP）→ AD DS。用户在 AD FS 的页面认证，AD FS 把令牌交回 Keycloak，Keycloak 据其中的声明建立或更新本地的用户表示，再以本系统自己的 OIDC 令牌对服务层发放。服务层只认 Keycloak 签发的令牌，从不直接校验 AD FS 的令牌——这样受众划分、角色映射与有效期策略有一个统一的落点。

协议取 OIDC；AD FS 若只开放 SAML 2.0 或 WS-Federation，Keycloak 同样支持，但声明的名称与格式随之不同，须按实际开放的协议定稿（IR-49）。

人的身份走这条链路；机器身份不走。esb、ai_pkg、mcp 三个受众是 OAuth2 客户端凭证，客户端与密钥由 Keycloak 自己管理，与 AD 无关——把机器身份塞进 AD 会让一个被禁用的「账号」同时打断多个系统的集成，而且它本来也不需要人的那套策略。

### 6.4  令牌与受众

| 受众 | 用途 | 特殊约束 |
| --- | --- | --- |
| portal | 门户、仪表板、大屏 | 常规有效期 |
| mobile | 移动端（IF-40） | 独立受众与更短有效期；记录级接口在该受众下一律拒绝（CN-31） |
| esb | 对外数据服务（IF-33） | OAuth2 客户端凭证，映射到角色后受同一矩阵约束 |
| ai_pkg | AI 包（IF-37 至 IF-39） | 同上；只能生成结构化查询体，不得生成 SQL（DD-28） |
| mcp | MCP 绑定 | 同上；返回携带四个元字段 |

### 6.5  令牌签名证书与元数据的轮换

AD FS 的令牌签名证书默认自动轮换（AutoCertificateRollover，有效期约一年，新证书在生效前若干天就会出现在元数据中）。Keycloak 若只在配置时导入过一次证书，轮换当天所有登录会同时失败，现象是令牌签名校验不通过——而那一天没有任何人改过本系统的配置，排查方向极易跑偏。

处置是把 Keycloak 的上游 IdP 配置为按元数据 URL 定期刷新，而不是粘贴一份静态证书。元数据 URL 在生产网内必须可达，这一点要写进网络策略——它和第 7 章要求 CRL/OCSP 可达是同一类要求：身份与证书校验依赖的那几个内部端点，不能因为「只是元数据」就被防火墙顺手挡掉。

运维手册中为此保留一条定期检查：核对 Keycloak 当前持有的签名证书指纹与 AD FS 元数据中的是否一致，并记录下一次到期日。该项与 MOI 的证书轮换周期对齐，具体周期待 IR-49 答复后填入。

### 6.6  角色与部门归属的权威来源

本系统的四个角色（第 2.1 节）由 AD 组经声明映射而来：AD 组 → Keycloak 角色 → 本系统角色。映射表是配置，不是代码，变更不需要发版。

部门级行过滤（第 2.3 节）需要「这个人属于哪个派驻部门」。过渡期以 M-06 的本地映射表承担，目录侧就绪后切换为以目录为权威——切换的前提是 AD 中存在可据以判断部门的组或属性，并且它能作为声明随令牌传出（IR-39）。

此处有一个容易被忽略的技术约束：用于标识「同一个人」的声明必须是不可变标识，不能用 sAMAccountName 或 UPN。人员改名、调岗、换邮箱都会改变后两者，而一旦标识变了，Keycloak 会把同一个人当成新用户，此前的授权与审计关联随之断开。应取 objectGUID 一类的不变标识作为 sub，把可读的账号名仅作显示用。这一条写入 IR-49 的声明清单要求。

### 6.7  Keycloak 自身的暴露面

Keycloak 经 DMZ 反向代理暴露时只放行 token、authorize 与 jwks 三个端点，管理控制台绝不暴露（CN-31）。这一条在网络策略与反向代理配置中各写一次，两处都要有。

身份代理还有一项网络含义：登录过程中用户的浏览器会被重定向到 AD FS，因此凡能登录本系统的客户端，其浏览器都必须能到达 AD FS 的登录端点。移动端经 DMZ 反向代理访问（CN-30、CN-31），这条链路上的可达性要与总包商一并确认——本系统自身可达并不代表用户的浏览器可达，二者是两条不同的路径。

## 7  传输加密

生产上数据库连接是跨虚机的：pgBouncer 与 HAProxy 在 LB 节点，PostgreSQL 在库虚机，中间是一段真实的内网链路（DD-67 · LD-08 第 8 章）。这条链路上跑的是全部警情明细、报警人号码与位置坐标。开发机上三者同机，回环不出网卡，因此这一章的要求只对生产成立——但正因为开发机验不到，它更容易被遗漏。

库连接与复制流量一律启用 TLS，客户端侧取 sslmode = verify-full（DD-68）。不取 require 的理由是：require 只加密不验证对端身份，中间人仍可冒充库端完成握手——它挡住的是被动监听，挡不住主动劫持，而在一个已经分段的内网里，值得防的恰恰是后者。verify-full 同时校验证书链与主机名。

证书由 MOI 的内部 CA 签发（现场已有 AD CS）。本方不自建 CA，也不使用自签证书——自签证书要么逼着客户端关校验，要么要在每台机器上单独布信任，两者都会在扩容时失守。

吊销检查的地址必须在内网可达。离网环境中 CRL 或 OCSP 指向外网时，TLS 握手不是报错而是**超时**，表现为连接间歇性卡住数十秒，而错误信息里不会提到证书——这是本设计中最难排查的几类故障之一，故在第 9 章列为对基础设施提供方的要求（NW-06）。

证书轮换按年计。轮换当天若只换了库端而未更新客户端的信任链，连接会整体失败；故轮换规程与演练一并列入 LD-08 的演练规程，与切换演练同等对待。

| 环节 | 要求 |
| --- | --- |
| HAProxy → PostgreSQL | TLS，sslmode = verify-full。证书的主机名须与 HAProxy 后端中配置的地址一致——两者不一致时 verify-full 会拒绝，而这是最常见的首次配置错误 |
| 主库 → 同步备库（复制） | TLS。复制流量与应用流量走不同网段（NW-01），证书各自签发 |
| 应用 → pgBouncer | 生产上同机回环，不强制 TLS；若日后拆机部署，按本表第一行同等处理 |
| 备份传输与归档 | 落盘前即为加密形态或经加密通道传输，与 T-15 的静态加密分别成立——一个管在途，一个管在存 |

## 8  审计

查询与导出行为写入 audit.access_log，只增不改。911 数据的敏感度决定了「谁看过什么」必须可回溯。

| 要求 | 说明 |
| --- | --- |
| 记录范围 | 查询、记录检索、导出、报表渲染、对外 API 与 MCP 调用，六类均记 |
| 敏感字段记名不记值 | sensitive_fields 列记录本次返回的敏感字段名清单。审计表本身不得成为系统内最集中的泄露点 |
| 零行结果也记 | 返回零行同样是信息——它说明了查询意图，也是判断越权尝试的依据 |
| 审计查询本身留痕 | 管理员在 M-07 查看审计的行为同样记录。否则权限最高的人是唯一没有痕迹的人 |
| 受控 SQL 记原文 | SQL 全文、执行时间、返回行数、涉及的表与列全部记录。「由调用方负责」若无留痕则无法追责 |
| 权限变更留痕 | 字段矩阵与部门映射的每一次变更写入 audit.permission_change_log，含变更前后值与理由 |

投递交接点另记 audit.delivery_log：短信与邮件网关由总包商提供、其故障不计入本方服务水平，但本方必须能证明消息确已交给网关（CN-30）。

## 9  脱敏与匿名化

生产环境为完整数据、按角色访问、全部访问写审计。测试与培训环境的规则依 MOI 数据分类政策确定，下表为起草值。

| 环境 | 数据 | 手法 |
| --- | --- | --- |
| 测试 / 集成 | 生产数据的脱敏子集 | 号码与证件类用保留格式的替换；姓名用字典替换；描述与反馈正文置空或用语料替换；坐标做泛化偏移，保留网格归属但不可回溯到具体位置 |
| 培训 | 匿名化数据集 | 不含任何可回溯到真实个人或真实警情的内容。警情编号重排，时间轴整体平移 |

两条纪律：脱敏规则的对象清单由 M-11 的扫描结果生成，不人工枚举——八年合同期内字段必然新增，人工清单必然遗漏，而遗漏的正是新字段（DD-40）；脱敏与匿名化脚本须版本化、可重复执行、结果可核查，它们本身是交付物。

要与生产的字段可见性矩阵区分清楚：矩阵是查询时裁列，脱敏是数据落地时改值。两者机制不同、目的不同，实现时不得混用。

## 10  两项前置门与本方的输入稿

RFP 2.7.9.5 规定数据分类政策须经 MOI 批准后方可在生产与培训环境实施任何数据库；2.7.9.11 规定 DLP 登记册须经 MOI 批准后方可部署任何数据存储。两者都是关键路径上的里程碑前置条件，不是可与开发并行的文档工作。

两者都需与 MOI 共同制定而非单向索取，因此本方应主动提交输入稿。本册中可直接作为输入稿内容的有四项：

| 输入稿内容 | 来源 |
| --- | --- |
| 敏感字段清单与分类建议 | 本册 2.2 的起草矩阵，加 M-11 扫描结果 |
| 角色与字段的可见性建议 | 本册 2.2 |
| 受控 SQL 的授权规则与名单 | 本册第 5 章。「谁能看全量数据」须由 MOI 认可 |
| 测试与培训环境的脱敏与匿名化规则 | 本册第 9 章 |

这样做的收益是把前置门的依赖从「阻塞整个功能开发」收敛为「一张表的取值」——矩阵的结构本方先交付，默认取值待批准后填入。功能开发不被阻塞，而政策一旦批准即可落地。
