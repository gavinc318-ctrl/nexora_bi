# 数据模型详细设计

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Detailed Design — Data Model   ( LD-02 ) · 版本  v0.1 · 2026 年 9 月 · 本册定义 core 层的业务对象模型、逐表结构、粒度与口径落点， · 以及 raw、staging、mart、ai、meta、audit 六层的结构规范。

## 1  本册的范围与读法

本册细化 HLD v0.3 第 5 章。它回答的是"表长什么样、每一行代表什么、口径落在哪一层"，不回答"指标怎么算"（LD-03）与"接口怎么调"（LD-04）。

结构性内容以 SQL 形式交付，不在正文中贴全文。DDL 位于同目录 ddl/ 下，是 Git 中受控的结构性配置（HLD 9.2），变更须走发布流程。正文只写规则、取舍与理由——这些是 SQL 里写不下的部分。

| 文件 | 内容 |
| --- | --- |
| ddl/01_schemas_and_helpers.sql | 七个 schema、代理键函数、坐标系配置 |
| ddl/02_core_dimensions.sql | core 维度表，含缓变维列约定 |
| ddl/03_core_facts.sql | core 事实表，含五层单据树、桥表与 AI 回流表 |
| ddl/04_meta_and_audit.sql | meta 与 audit 全部对象 |
| ddl/05_partitions_and_indexes.sql | 分区函数与索引策略 |

上述脚本已在 PostgreSQL 16 加 PostGIS 3 上完整执行通过，并以样例数据验证了单据树、桥表关联、分区路由、代理键的确定性与行级过滤条件的可下推性。

## 2  业务对象模型

CAD 的单据是一棵树，每个上级节点可指向多个下层节点；改派与增派都是新增节点，不是修改原节点。通话与接警单之间是多对多——掉线重拨、回拨与多人报警都由 CAD 合并到同一张接警单。

| 层 | 事实表 | 一行代表什么 |
| --- | --- | --- |
| 0 | core.fact_call_leg | 一张 ICP 话单 ＝ 一通电话经过的一个设备（IVR · 技能队列 · 坐席） |
| 0 | core.fact_call | 一通电话（来源 ICP）。由腿级聚合构建，不独立接入（DD-66） |
| — | core.bridge_call_intake | 一条通话与接警单的关联，带角色与来源 |
| 1 | core.fact_intake | 一张接警单。本系统中即案件粒度 |
| 2 | core.fact_dispatch_order | 一张派警单 ＝ 接警单 × 警种 |
| 3 | core.fact_turnout | 一张出警单 ＝ 派警单 × 警员 |
| 4 | core.fact_feedback | 一张反馈单 ＝ 出警单 × 第 N 次反馈 |
| 旁 | core.fact_agent_session | 一段坐席签入区间（来源 ICP 明细接口） |
| 旁 | core.fact_agent_day | 一名坐席一天的状态时长累计（来源 ICP 平台历史指标，DD-65） |
| 旁 | core.fact_ai_inference | 一条 AI 推断结果（经 IF-07 回流） |

> 一个命名陷阱    反馈单（警员的处置反馈）与客户反馈（满意度回访，RFP 1.6.2.17）在中文里同名，含义完全不同。表名与指标名中前者一律用 feedback，后者用 citizen_feedback。不分清楚，客户反馈看板 D-15 会取到一堆警员的处置记录。 凭方案讨论的记忆去理解需求会漏掉硬指标。条款级的逐条复核不可省略。HD-02 追溯矩阵中"需人工复核的条款"一页保留了 32 条尚未被需求直接引用的条款，开发组应在开工前逐条确认它们确实已被领域需求覆盖。这一页不应长期保持非空。

## 3  粒度是本册最重要的一件事

时长类指标的落点由单据树决定，不能挂错层：

| 指标 | 起止 | 粒度 |
| --- | --- | --- |
| 受理时长 | 应答 → 接警单建立 | 接警单 |
| 派单时长 | 接警单建立 → 派警单下发 | 派警单（每警种一个数） |
| 到场时长 | 派警单下发 → 出警单到场 | 出警单（每警员一个数） |
| 处置时长 | 到场 → 出警单结束 | 出警单 |
| 全过程时长 | 振铃 → 结案 | 接警单（结案的定义见 3.2） |

### 3.1  同一件事，三种平均口径给出三个不同的数

以一起同时派给警察与民防、共出动五名警员的警情为例，用样例数据实测：

| 口径 | 分母 | 结果 |
| --- | --- | --- |
| 按出警单平均 | 5 张出警单 | 15.20 分钟 |
| 按派警单平均 | 2 张派警单 | 14.17 分钟 |
| 按接警单平均（取首个到场） | 1 张接警单 | 6.00 分钟 |

三个数都对，回答的是三个不同的问题。因此指标注册表中每一条都必须显式声明粒度（meta.metric_registry.grain 为非空列），报表标题与口径说明中必须写明按什么平均。含糊其辞的"平均到场时长"不允许进入指标注册表。

M-R05 单位出动次数按出警单计——一张派警单出三名警员即三次出动。R-24 处置单位出动与负荷同理。这一条最容易算错。

### 3.2  两个需要业务确认的口径

| 口径 | 当前处理与待确认点 |
| --- | --- |
| 接警单的结案时间 | 每张出警单自行管理其结束。CAD 若无接警单级结案字段，则取该接警单下全部出警单结束的最晚时间，并置 is_closed_derived 为真。派生值不得不加标记地进入对外指标。待 DS 确认是否存在独立结案字段。 |
| 警情级响应时长 | 默认按警种分别呈现，另定义"首个到场时长"作为接警单级指标。两者在指标注册表中分别命名，不合并为一个"响应时长"。 |

### 3.3  话务的粒度不是「一通电话」

ICP 的话单是「呼叫每经过一个设备一行」，一通电话走 IVR、技能队列、坐席会产生多行，靠 CALLID 串起来，CALLIDNUM 为腿内序号（1 为首腿，-1 为末腿）。这不是接口的实现细节，而是话务领域的真实粒度：等待发生在排队腿上，通话发生在坐席腿上，转接表现为同一通呼叫出现第二个坐席腿。

因此话务拆成两张表（DD-66）。core.fact_call_leg 与话单一行一一对应，是唯一的接入落点；core.fact_call 为通话级，由腿级聚合构建，每一列都必须能从腿级重算。按坐席的指标一律从腿级算，通话级只服务于通话粒度的报表与快速归属。

这样做的代价是多一张表和一次聚合，换来的是两件事：一、接入侧不做解释，口径分歧永远能回到话单行上查；二、通话级与腿级不会各自算出一个数——两条路算同一个指标是口径分裂最常见的来源，这里从结构上堵死。

坐席侧同理但方向相反。签入签出平台给的是区间明细，落入 core.fact_agent_session，可按班次窗口求交（DD-53）；而各状态时长平台只给日累计，落入 core.fact_agent_day，不可下钻、不可按班次切分（DD-65）。同一张报表里这两类指标的可切分性不同，须在报表规格中写明。

## 4  代理键：确定性 UUID，不用自增序列

全部 core 事实与维度的代理键由 core.sk(站点, 源系统, 自然键) 生成，是基于站点命名空间的 UUID v5。缓变维用 core.sk_scd()，把生效时间纳入计算，使同一实体的每个版本得到各自的键。

选它的首要理由不是多站，是重建。DD-02 定了 raw 只追加、向上重建；DD-37 说未澄清的映射将来搞清楚了要重算全部历史。也就是说 core 会被重建，而且是设计上鼓励的行为。若代理键是自增序列，每一次重建都会重新分配主键，mart 与 ai 的历史分区、audit 中记录的对象、AI 包回流数据引用的实体键会同时失效。确定性键使重建幂等——同一条源记录无论重建多少次、在哪个环境，得到同一个主键。

自然键取自接入契约的 idempotency_key（HLD 4.2）。契约用它去重，core 用它生成主键，两处口径天然一致；契约中未定义幂等键的源不允许进入 core。

| 要求 | 是否满足 |
| --- | --- |
| 全局唯一、跨站合并不冲突（REQ-MOD-05） | 满足。命名空间含站点，无须号段协调 |
| 不依赖单站自增序列 | 满足 |
| 重建幂等 | 满足。这是选它的首要理由 |
| 排障可复算 | 满足。拿源自然键即可算出主键并核对 |
| 不影响检索速度 | 满足。记录检索走业务字段索引，主键不参与；见第 12 章 |

代价是 16 字节而非 8，且哈希型 UUID 没有时间局部性。在本项目不构成问题：峰值 5 万呼叫每日平均不足 1 行每秒，事实表按天分区使单分区索引很小，连接主要发生在夜间模型构建而不在查询路径上（DD-01 已把加工层排除在查询链路之外）。

曾考虑 UUID v7（时间有序、索引友好），但它不是确定性的，会丢掉幂等重建。在两者之间取幂等。

命名空间同时隔离站点与源系统，因此归档库与 DS 展示库中出现同样的单号不会撞键。但这带来两处必须先确认的风险：其一，若割接存在并行期，同一起警情在两个源中各有一份，会得到两个主键并在报表中呈现为两起警情——此时需要一条「归档记录在 DS 中已存在时以 DS 为准」的合并规则，且必须作用在 staging，不能留到 core。其二，若源系统的单号按年重置，同一个源内部就会撞键，跨源命名空间救不了——此时自然键必须把年份或受理日期纳入。两项均已列入第 14 章。

## 5  分区表主键的一个固有限制

PostgreSQL 要求分区表的唯一约束必须包含分区键，因此全部事实表的主键为 (代理键, date_key) 而非代理键单列。代理键本身在全局唯一，但该唯一性由模型构建阶段的测试保证，数据库层不跨分区强制。这是分区表的固有限制，不是设计取舍，须在测试方案（LD-10）中有对应用例。

同理，事实表之间不建外键约束：跨层复合外键会把子单据的日期强行绑到父单据的日期上，而两者未必相同。参照完整性改由模型构建阶段的测试保证，测试失败即阻断发布。事实表到维度表的外键予以保留——维度小，写入是批量的，约束提供实际保护。

## 6  时间与时区

RFP 2.7.7.5 要求迁移数据保持百分之百保真，明确包括带原始时区的时间戳。但 PostgreSQL 的 timestamptz 只存 UTC 瞬时，输入的偏移量会被丢弃。

| 层 | 处理方式 |
| --- | --- |
| raw | 保留源系统送来的原始文本形式（JSONB 载荷中本就完整），保真在此层成立 |
| core | 时间列一律 timestamptz；另设 source_tz_offset 列记录原始偏移，备查与举证 |
| 报表与接口 | 统一沙特时间 UTC+3 呈现；日切以 00:00 AST 为界（HLD 6.3） |

这样保真在 raw 层成立、可用性在 core 层成立，两边都不牺牲。成本极低，但事后补要改全部事实表。

## 7  缓变维

维度按"当时"记录，即 Type 2（DD-12）。每张缓变维带 valid_from、valid_to 与生成列 is_current，事实关联当时那一版。目的只有一个：去年打印的报表今年重跑数值不变。

有一处必须分清：dim_agent.agency_type_sk 是统计口径用的派驻警种，按当时记录；而权限判定用的是当前警种，取自身份系统。两者正交，实现时不得混用（DD-41）。

双语名称：源系统仅提供单一语言时，由 M-10 维护双语对照（REQ-RPT-09）。每张维度的 name_ar 与 name_en 均为非空列，强制这件事在数据进入 core 之前完成。

## 8  空间与坐标系

三项坐标系参数化，存于 meta.srid_config（DD-33）：源坐标系写在接入契约中一源一值；存储坐标系默认 WGS84；分析坐标系默认 UTM 37N。网格聚合、面积与距离计算必须在投影坐标系下进行——在麦加纬度直接用经纬度算会明显失真。

辖区归属以 CAD 的字段为准，不由 dim_sector.boundary 重算（DD-32）。CAD 在受理当时用当时的区划面算出，重算会得到"按现在"的口径，属 DD-12 明确拒绝的做法。boundary 只用于网格聚合与呈现，并作为每日对账项监控两者的一致率。

底图、瓦片与地图应用由 HudHud 本地部署提供，不在本系统内（CN-29）。本方向其提供聚合结果。

## 9  raw 与 staging 的结构规范

| 层 | 规范 |
| --- | --- |
| raw | 与源逐字一致，附完整原始载荷（JSONB）与接入元数据：run_id、contract_version、源水位、原始时区偏移、落地时间。只追加，永不覆盖、永不修正（DD-02）。一源一表，表名 raw.<源标识>__<源表名>。 |
| staging | 类型规范、去重、软删除与迟到处理、语义映射。一源一模型，不做跨源关联。全部转换写在 dbt 模型中，不写入契约 YAML（DD-05）。未映射取值落显式的未映射桶，不得归入"其他"（DD-06）。 |

## 10  mart 与 ai 的处理方式

本册不穷举 mart 的聚合表。它们由 LD-03 的指标定义与 LD-05A 的报表清单决定，而报表清单尚未经工作坊冻结；现在把四十张报表对应的聚合表逐一写死，是在为一份会变的清单建表。本册只定义模式：

| 规则 | 说明 |
| --- | --- |
| 构建来源 | mart 与 ai 均自 core 构建，不得直接引用 raw（DD-03）。代码评审规则强制 |
| 命名 | mart.<主题域>__<粒度>__<聚合内容>，粒度必须出现在表名中 |
| 热温分层 | 近一年的聚合表为热层，承担 95% 亚秒；更早的走历史查询路径（DD-38 · DD-36） |
| 封账 | 日粒度聚合带 close_version，封账后的分区冻结；修正以新版本行表达，不改旧行 |
| 重放 | 复现历史版本的能力来自 raw 与 run_id 水位的重放，不要求 core 双时态 |
| ai 层 | 实体级宽表、特征表、媒体索引与导出快照。演进节奏与权限等级均不同于 mart，故并列而非合并（HLD 5.6） |

## 11  meta 与 audit

meta 与 audit 连同 raw 是仅有的三个不可重建的 schema。meta 中值得单独说明的三张表：

| 对象 | 要点 |
| --- | --- |
| meta.value_profile | 记录每个取值的首次与最后出现时点。分布突变点即为归档数据中 schema 版本边界的候选，用于在拿不到 Hexagon 升级记录时反推（DD-37） |
| meta.search_criteria | 记录检索的条件集配置。每条启用的条件必须指向一个实际存在的索引，新增条件须伴随索引评审（DD-34） |
| meta.field_visibility | 字段级可见性矩阵。结构由本方交付，默认取值待 MOI 数据分类政策批准后填入（DD-35 · CN-13） |

audit.access_log 的 sensitive_fields 列记录本次返回的敏感字段名清单——记名不记值。审计表本身不得成为系统内最集中的泄露点。audit.delivery_log 保存投递交接点证据：短信与邮件网关由总包商提供、其故障不计入本方服务水平，但本方必须能证明消息确已交给网关（CN-30）。

## 12  索引与检索路径

记录检索（DD-34）走业务字段索引，不走主键。meta.search_criteria 中每一条启用的条件都在 ddl/05 中有对应索引。时间范围一律先做分区裁剪，索引只负责分区内的选择性。

| 场景 | 走什么索引 | UUID 主键是否参与 |
| --- | --- | --- |
| 按警情编号或通话标识调记录 | 自然键上的 B-tree | 否 |
| 按时间范围加条件筛选 | 分区裁剪加复合索引 | 否 |
| 从列表点进详情 | 主键单点查找 | 是，一次索引探查 |
| 夜间模型构建的表连接 | 主键连接 | 是，但不在查询路径上 |

派警单与出警单上的索引以 agency_type_sk 打头，因为行级过滤的下推条件永远带它（DD-41）。
