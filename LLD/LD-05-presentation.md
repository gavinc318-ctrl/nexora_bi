# 展现层详细设计

> OSS911 麦加 911 运营中心 · 商业智能与数据仓库子系统 · Detailed Design — Presentation Layer   ( LD-05 ) · 版本  v0.1 · 2026 年 9 月 · 本册定义门户信息架构、双语与从右至左布局、报表与仪表板的机制、 · 地图嵌入、指挥大屏、移动端布局，以及渲染预算与组件库。

## 1  本册的范围与读法

本册细化 HLD v0.3 第 8 章，回答的是「数字以什么面貌出现在人眼前」。逐张报表与仪表板的规格在 LD-05A，管理界面在 LD-06，本册只写机制与规范。

展现层没有自己的数据。它拿到的每一个数都来自 LD-04 的查询 API，包括那四个响应元字段。因此本册反复出现的一条原则是：展现层不做任何会改变数值含义的加工——不在浏览器里做二次聚合、不做单位换算、不自行补零。理由与 LD-04 第 3 章的口径唯一性相同：一旦前端算了一遍，同一个指标就有了第二个实现，而两个实现迟早会不一致。

## 2  门户与信息架构

### 2.1  自建外壳，Superset 只做查询引擎

门户采用自建外壳，Superset 作为后端查询引擎，不直接暴露给用户。这比直接交付 Superset 多出两到三周工作量，换来三件事：界面风格与阿语本地化不必迁就第三方产品的约定；权限模型不必在两套体系之间做映射；门户、仪表板、大屏与移动端共用同一套视觉与交互体系。

第二条是决定性的。本系统的权限是三层的——角色、字段级可见性矩阵、部门行过滤（LD-07）——而把这三层映射到另一个产品自带的权限模型上，映射本身就会成为一个持续的缺陷来源，且任何一次产品升级都可能改变映射的行为。让 Superset 只负责执行查询，权限判定完全留在本方服务层，这个问题就不存在。

### 2.2  角色决定入口，而不是决定菜单项的灰显

四个角色看到的是不同的门户首页，而不是同一个首页上灰掉一部分。没有权限的功能不出现在导航里，请求对应路径时由服务层拒绝。

灰显的做法会把系统的能力边界暴露给没有权限的人——一个接警员不需要知道存在「全局绩效」这个页面。更要紧的是，灰显容易演变成「前端隐藏、后端不拦」，那就不是界面问题而是越权漏洞了（LD-10 的越权测试专门覆盖这一项）。

## 3  双语与从右至左

界面为阿语与英语双语，用户可切换，阿语界面为从右至左布局。这一章比它看起来要重要：双语与 RTL 的缺陷极少是致命的，但数量多、分散、且往往在交付演示时才被阿语母语者一眼看出。

### 3.1  从右至左不只是翻转方向

把根元素设成 dir="rtl" 只解决了文字流向。以下几项需要逐项处理，它们是 RTL 项目最常见的返工来源：

### 3.2  混排必须做双向隔离

阿语标签里嵌一个拉丁编码——例如「محطة U-1007」——是本系统的常态：维度名称是阿语，编码是拉丁字母加数字。若不做双向隔离，Unicode 的双向算法会把编码放到句子的另一端，看起来像是数据错了，实际是渲染问题。

处理方式是对每一段嵌入的拉丁文本加隔离标记（HTML 的 bdi 元素或等效的隔离字符），不依赖浏览器猜测。这一条写进组件库的基础文本组件，而不是留给每个页面各自处理——留给各自处理的结果一定是有的页面对、有的不对。

### 3.3  数字采用西阿拉伯数字

阿拉伯语区存在两套数字符号：西阿拉伯数字（0123456789）与东阿拉伯数字（٠١٢٣٤٥٦٧٨٩）。本设计在两种语言界面下一律采用西阿拉伯数字。

理由有三：沙特官方文书与统计出版物普遍使用西阿拉伯数字；导出的 Excel 与 CSV 若含东阿拉伯数字，在下游工具中会被当作文本而非数值；以及同一个数在两种语言界面下呈现为不同符号，会让阿英对照核对变得困难。此项列入待确认，因为它是一个观感偏好而非技术判断，应由 MOI 业务方拍板（见第 11 章）。

### 3.4  日期、时区与回历

### 3.5  报表按语言各出一份

报表不做阿英混排，每张报表有阿语版与英语版两套模板，各自单向排版（与 MOI 商定）。这一决定显著降低了排版复杂度与缺陷风险：混排报表中的表格、页眉页脚、页码与图表标题各自需要独立的方向处理，而其中任何一处出错都会在打印件上暴露。

随之而来的数据问题在 LD-01 9.2 已经处理：维度取值来自 CAD，若源端只有一种语言，另一种由 M-10 维护的双语覆盖提供；覆盖处于待重新确认状态时回落显示源端原文。因此阿语报表中可能出现少量非阿语的维度名称——这是诚实的回落，好过显示一个可能已经失效的旧译名。

## 4  元字段怎么呈现

LD-04 规定每个响应携带四个元字段：口径版本、数据时点、封账状态、是否依赖未验证映射。它们是数据的一部分，不是调试信息。但四个字段全部显示在每一个数字旁边，界面会变成一片说明文字，人反而不看了。

因此按「这个字段是否改变使用者此刻的行为」分级呈现：

### 4.1  导出时四个字段全部写入

导出的文件会离开系统：它被下载、转发、打印、贴进另一份报告。界面上的提示、悬停与颜色全部随之丢失，只剩下数字。

因此凡导出——PDF、Word、Excel、CSV——四个元字段一律完整写入页脚或首个工作表的说明区，不做分级。这一条不允许由用户关闭。一份没有口径声明的导出件，在三个月后的会议上就是一个来历不明的数字。

### 4.2  超出可用年份的时段

查询范围超出 meta.metric_availability 的可用年份时，服务层返回的是明示信息而非空结果（LD-04 3.4）。展现层原样呈现「该时段源端无此数据」并指出限制字段，不显示为零，也不显示为空白图表。

图表上的处理是：该时段在坐标轴上保留位置但不绘制数据点，并以浅色底纹与文字标注覆盖。断线的折线图会被读成「下降到零」，而留白加标注不会。

### 5.2  不在浏览器里做聚合

展现层不做任何二次聚合。图表要什么粒度就向服务层请求什么粒度，不允许取回明细后在前端求和、求平均或计算占比。

这条限制看起来保守，理由却很实在。前端一旦算了一遍，同一指标就有了第二个实现——而它不受指标注册表管辖、不带口径版本、不进对账。日后两个数字对不上时，没有任何机制能指出是哪一边错了。第二个理由是权限：前端聚合意味着明细数据必须先传到浏览器，而字段裁剪与行过滤本来就该在服务端完成，明细一旦下发，裁剪就失去意义了。

## 6  地图嵌入（IF-41）

### 6.1  分工边界

地图由沙特本地厂商 HudHud 提供，本地部署。本方不建底图、不做瓦片服务、不做地图应用。本方提供的是空间聚合结果——网格化计数、点在面内判定、热点强度——由 mart 层用 PostGIS 算出，交给 HudHud 组件渲染。

这条边界要在实施期反复确认，因为它容易被侵蚀：一旦开始在本方界面里画多边形、做图层管理、处理底图缩放，实际上就是在重建一个地图应用。判断标准很简单——凡是与「数据聚合」无关的地图能力，都属于 HudHud 一侧。

### 6.2  离线部署

组件与瓦片必须可离线部署，以满足无外网要求（REQ-SEC-06）。任何需要联网获取字体、图标或样式的地图组件都不可用，即便它在开发环境里工作正常——开发环境有网。

这一项在联调期须专门验证：断网环境下地图完整加载。列入 LD-10 的测试用例。

### 6.3  地图故障时的降级

HudHud 的故障不计入本方服务水平，但界面不能整页失败。地图不可用时，含地图的仪表板降级为表格与统计呈现，并明确提示「地图服务不可用」。

降级而非失败的理由是：地图往往只是仪表板的一个面板，其余面板的数据完全正常。整页失败会把一个外部组件的故障放大成本系统的故障，而这在服务水平的判定上对本方不利——尽管责任不在本方，使用者看到的是本方的页面打不开。

### 6.4  热点与聚集区

热点与聚集区的算法与阈值在 LD-03 定义，本册只管呈现。呈现上须注意两点：热力图的色阶必须给出图例与数值区间，否则「红色」代表多少无从判断；以及网格粒度须随缩放级别切换并显示当前粒度，否则同一片区域在不同缩放下呈现不同的密度，会被误读为数据变化。

## 7  指挥大屏

### 7.1  无人值守自恢复

大屏是独立 Web 应用，长连接，装在墙上，没有人守着键盘。因此它的设计目标不是功能丰富，而是「出了任何问题都能自己回到正确状态」。

第三条是这一节里最要紧的。一块显示着两小时前数据的大屏，比一块黑屏危险得多：黑屏所有人都知道它坏了，而陈旧数据看起来一切正常。

### 7.2  指示性数据的标注

大屏主视图为实时共同作战图，2 至 10 秒刷新，数据来自实时状态服务——它是对源系统的观测，不落库、不参与统计（LD-04 5.1）。因此大屏上的数字须常驻标注为指示性，不作为考核依据。

标注要写在画面上，不能只写在文档里。大屏是被截图、被拍照、被引用到汇报里的，而截图不会带上文档。

### 7.3  POC 已经锚定了预期

DS 曾提供一块 POC 大屏并已由 MOI 相关人员看过，其数据为写死的样例。该大屏不在交付范围内，本系统交付的大屏取代它，但相关人员的预期已被那个界面锚定，功能覆盖低于它会被视为倒退。

因此实施期须逐项核对 POC 界面上的每一个元素是否有真实数据源支撑——写死的数字不需要数据源，真实实现需要。这份核对清单是 LD-05A 的输入之一，也是 T-16 的内容。凡核对下来没有数据源的元素，须在设计评审时明确处置：要么找到数据源，要么与 MOI 说明为何不做，不能留到验收现场。

## 8  移动端

移动端本期交付，形态为原生薄壳内嵌移动专用布局。定位是面向主管与管理员的管理看板，不是接警员与调度员的作业工具（DD-30）。

最后一条须在 T-08 的服务水平判定口径中写明。移动端链路上有一段本方完全不控制的公网，把它计入亚秒承诺等于为运营商的网络质量背书。

## 9  渲染预算

### 9.1  前端在承诺之内，不在承诺之外

RFP 1.6.7.2 规定响应时间的测量含前端渲染。这一句把展现层拉进了性能承诺：95% 亚秒、峰值 99% 低于 2 秒，测的是用户看到结果的时刻，不是服务端返回的时刻。

### 9.2  由预算推出的三条界面规则

第三条与 LD-04 的三档路径对应：实时推送路径 2 至 10 秒刷新且标注指示性，快速查询路径承担亚秒承诺，历史查询路径走独立低优先级配额、不得拖慢快速路径。这三档在界面上必须让使用者能分辨——同样是一张图，一个是实时指示值，一个是封账权威值，看起来一样就会被同等对待。

## 10  组件库与设计系统

门户、仪表板、大屏、移动端、管理界面共用同一套设计系统与组件库。这是 2.1 选择自建外壳换来的收益，不能在实施中被稀释成五套各自演化的界面。

图表封装是这一章的重点。RTL 镜像、超出可用年份的留白标注、未封账标记这三件事如果留给每个页面自己做，四十张报表加二十个仪表板意味着六十次实现机会，其中必然有做错的。集中在封装层则只需做对一次。

色彩另有一条硬约束：不得以颜色作为唯一的信息载体。未封账、依赖未验证映射、超出可用范围三种状态都必须同时有文字或图形标记——色觉障碍之外，大屏的拍照与打印件的黑白复印也会让颜色失效。

| 参数默认值 | 按角色给出合理默认，使报表打开即有数据。默认值不得跨越权限边界——调度员的默认辖区是其本部门。 |
| 版式 | 屏幕版式与打印版式分别定义。打印版式固定纸张与页边距，表格跨页时重复表头。 |
| 发布与下架 | 在 M-05 管理，含按角色的可见性配置。 |

| 能力 | 规则 |
| --- | --- |
| 导出格式 | PDF、Word、Excel。异步任务，产物入对象存储，经媒体服务以短时效凭证下载。 |
| 大结果集 | 超过界面阈值时不在页面渲染，直接转为导出任务并提示。静默截断一律禁止。 |
| 订阅 | 按计划生成并投递。渲染时使用订阅者本人的权限上下文，不是配置者的（LD-04 5.3）。 |
| 投递记录 | 用户可在「我的订阅」中看到自己的历史投递与失败原因。 |

| 故障 | 自恢复行为 |
| --- | --- |
| 连接中断 | 自动重连，重连后提交最后序号，网关回送完整快照（LD-04 5.2）。中断两小时的大屏在一次往返后恢复正确。 |
| 渲染异常 | 前端异常边界捕获后自动重载页面，不停留在错误界面。 |
| 数据长时间未更新 | 界面显式显示「数据已停止更新 N 分钟」，而不是继续展示一个看起来正常但已经陈旧的画面。 |
| 浏览器或机器重启 | 开机自启并自动进入全屏，不需要登录操作——大屏使用专用的设备身份，不绑定自然人账号。 |

| 方面 | 规则 |
| --- | --- |
| 布局 | 与桌面门户分为两套布局，共用服务层 API、设计系统与组件库。手机屏与电脑屏的信息密度差异太大，同一套响应式布局两头都不好用。 |
| 内容 | 只呈现封账后的聚合指标。无记录级下钻、无媒体访问、无导出——这同时把数据分类政策的审批范围控制在统计数据一级。 |
| 拒绝方式 | 记录级接口在移动端令牌受众下由服务层拒绝，不是界面上不放入口（LD-04 第 9 章）。 |
| 推送 | 不使用 APNs 与 FCM。打开应用后主动拉取；告警经短信与邮件网关送达。 |
| 薄壳职责 | 证书固定、设备注册、令牌吊销。业务界面全部在内嵌页面中。 |
| 网络 | 经 internet 与 DMZ 反向代理，含公网段，不适用 RFP 1.6.7.5 的亚秒承诺，须在服务水平判定口径中单列或排除。 |

| 环节 | 预算 |
| --- | --- |
| 服务端查询与序列化 | 目标 400 至 500 毫秒（LD-04 3.2）。 |
| 网络往返 | 内网，按实测取值；移动端链路单列，不适用亚秒承诺。 |
| 前端解析与渲染 | 剩余额度。首屏可交互须在总预算内完成。 |

| 规则 | 理由 |
| --- | --- |
| 单屏面板数量设上限，超出部分延迟加载 | 首屏渲染十二个图表必然超预算。视口外的面板在滚动到时才请求与渲染。 |
| 大表格虚拟滚动，且结果集有硬上限 | 一次渲染上万行会让浏览器卡住，而这既超预算又无实际用途——没有人会滚动一万行。 |
| 历史查询路径转异步并明确提示 | 一年以上的查询允许秒级，超阈值转为异步任务，界面显示进度而不是转圈等待。转圈等待会让人反复点击刷新，把一次慢查询变成五次。 |
